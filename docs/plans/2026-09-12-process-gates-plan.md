## 1. Мотивация и позиция на шкале зрелости AI-SDLC

Сейчас процесс держится на дисциплине агента и памяти владельца:

- «зелёный `dotnet test`» в handover — обещание агента, инфраструктура его не
  фиксирует (`.github/` отсутствовал на момент плана; 2026-09-13 CI внедрён —
  §12);
- правила процесса размазаны по `AGENTS.md`, ADR-журналу и `lessons.md`;
  часть проверяется тестами (R1–R6), часть — вручную grep'ом (версионирование,
  урок №20) или памятью (show-me, урок №21);
- машинно-читаемый формат ревью-чека (`REVIEW_ID/SUBJECT/RECEIPT/VERDICT/REASON`)
  существует только в замороженном досье миграции; вердикты обычных фаз
  растворены в тексте ADR и коммит-сообщений.

План доводит контур до уверенного **уровня 3** (AI встроен в SDLC через
машинные гейты) и закладывает данные для **уровня 5** (метрики харнеса) —
не меняя ни одного owner-гейта и ни строчки продукта. Текущая позиция
(обсуждение с владельцем 2026-09-12) — уверенный уровень 2 («2+») с
элементами 3 и 5.

**Инвариант плана:** все owner-гейты сохраняются. CI и реестр стоят *рядом*
с правилом «нет коммита без owner-ревью», а не вместо него: CI отвечает на
вопрос «соответствует ли код заявленному», владелец — «принимать ли результат».

## 3. Фаза A — CI-гейт

> **Статус (актуализация 2026-09-13): внедрено** — workflow создан (коммит
> `79b6145`), строка AGENTS.md промотирована (`8d70d27`). Критерий приёмки
> (первый зелёный прогон, длительность, флейки) подтверждается владельцем во
> вкладке Actions — `gh` в системе недоступен. Остаток фазы: решение 11
> (branch protection — G2, вне дерева). Ниже — исходный текст плана.

Файлы: `.github/workflows/ci.yml` (новый), `AGENTS.md` (+1 строка).

Скелет workflow:

```yaml
name: ci
on:
  push:
    branches: [master]
  pull_request:

jobs:
  test:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: 8.0.x
      - run: dotnet restore SnowMeltingCalculator.sln
      - run: dotnet build SnowMeltingCalculator.sln -c Release --no-restore
      - name: Architecture rules (fast feedback)
        run: dotnet test SnowMeltingCalculator.sln -c Release --no-build
             --filter "FullyQualifiedName~Architecture"
      - name: Full suite (without UiSmoke)
        run: dotnet test SnowMeltingCalculator.sln -c Release --no-build
             --filter "Category!=UiSmoke"
```

Тонкости, проверяемые на первом прогоне:

- `dotnet build` должен пройти без ошибок. Фактическое состояние репо:
  `TreatWarningsAsErrors` нигде не включён (в csproj тестов он упоминается
  только в комментарии, предупреждения подавлены `NoWarn`); порог
  предупреждений в CI не вводим — отдельное решение владельца вне скоупа v1.
- Architecture-набор гоняется дважды (шаг быстрой обратной связи + внутри
  полного прогона) — осознанная цена; после первого прогона замер покажет,
  схлопывать ли в один шаг.
- Windows-раннер считает минуты с коэффициентом ×2; при приватном репо —
  лимит бесплатного тарифа. Первый прогон фиксирует длительность; при
  исчерпании лимита — возврат к владельцу (варианты: `workflow_dispatch` +
  ручной запуск, self-hosted-раннер — оба вне скоупа v1).
- Возможные сюрпризы: тесты, зависящие от окружения машины (культура, пути,
  установленные шрифты). Обработка — строго по флейк-политике (решение 12).

**Критерий приёмки:** первый зелёный прогон на push; длительность прогона
записана в handover; все вскрытые флейки обработаны (подтверждение — за
владельцем, §12).

### 3.1. Эксплуатация: что происходит при красном CI

Роли и сценарий (решения 14–15):

- **Первым падение видит агент** — по правилу зелёного handover он дожидается
  прогона в сессии; до владельца красный в норме не доезжает.
- **Владелец видит красный** в трёх местах: значок-крест у коммита (вкладка
  Code), упавший прогон во вкладке Actions (шаг + упавший тест + текст ошибки —
  те же, что в локальном `dotnet test`), email от GitHub (отключаемо).
  Опция при реализации — бейдж статуса в README.
- **Действие владельца** — одна фраза агенту («CI красный на коммите N,
  разберись»); логи и git руками не нужны. Цикл агента: лог прогона →
  воспроизведение локально тем же фильтром → фикс → пуш → зелёный.
- **Флейк:** перезапуск (агент `gh run rerun` или кнопка Re-run) — но не молча:
  флейк-политика решения 12 (изоляция/починка, запись в lessons; два флейка
  одного теста — уже закономерность).
- **Красный master** держится после закрытия сессии → новые фазы не стартуют
  до разбора (решение 14).
- **Падение вне кода** (лежал GitHub, обновился раннер, моргнул NuGet)
  диагностируется по логу, лечится перезапуском/правкой workflow.
- **Оговорка:** крест — сигнал, не замок: при пуши в master GitHub не
  блокирует красный коммит; жёсткий запрет появится вместе с PR-потоком
  (частично G2, полностью — уровень 4). Для связки «один владелец + агент»
  сигнал + правило красного master дают эквивалентную защиту.

## 4. Фаза B — реестр «правило → проверка» + верификатор

Файлы: `docs/agents/rules-registry.md` (новый), `tests/…/Architecture/RulesRegistryTests.cs`
и `VersionSyncTests.cs` (новые).

Формат реестра (примеры строк):

| ID | Правило | Первоисточник | Проверка | Как проверить |
|---|---|---|---|---|
| ARCH-R1 | `ProjectSession` — aggregate root с 4 слайсами | AGENTS.md, R1 | test | `R1_ProjectSession_IsAggregateRoot_WithFourExplicitSlices` |
| RULE-VER | каждый новый инсталл — новая версия | урок №20 | test | `VersionSyncTests` |
| RULE-SHOWME | план сопровождается show-me, владелец открывает артефакт | урок №21 | review-step | шаг ревью плана; машинной проверки нет — фиксируется честно |
| ARCH-SMC | hash-пин и round-trip контракта `.smc` | ADR-005, ADR-012 | test | `ProjectSnapshotFactoryTests`, `ProjectSnapshotContractTests` |

Грамматика колонки «Как проверить» (ревью P2-6): при типе `test` ячейка
содержит **точные имена тест-классов/методов, разделённые запятыми, без
прозы** — по ней работает reflection-резолв проверки A; проза допустима
только при `script` и `review-step`. Строка `RULE-VER` до фазы B существует
как ручная проверка (script/grep) и переводится в `test` в фазе B.

Инвентаризация при реализации покрывает: R1–R6 (+ WI-allowlists), цензус
подписок (`ReactiveSubscriptionLifecycleTests`), ratchet-гигиену XAML
(`ViewTokenHygieneTests`), AutomationId-контракты, persistence-пины `.smc`,
культуру биндинга (`RussianNumberCultureTests`), «docs/workspace и publish/
вне git» (script по `.gitignore`), ratchet `baseline_refactor_dedupe.json`,
уроки №18 (sanity-чек сетапа), №20, №21, №22–25 (тест-пины — колонка `test`;
№22-биндинги и №23-smoke — честный `review-step`), №26–28 (атакующее ревью,
регенерация show-me, два варианта — `review-step`), ведение
`docs/agents/quality-log.md`
(`review-step`), CI-гейт и правило зелёного handover (AGENTS.md, промоция
`8d70d27` — `review-step` по статусу прогона), «нет коммита без
owner-ревью», «writers — только через ADR», «lessons append-only», релизную
гигиену. Ожидаемый объём — 28–32 строки; типы проверки честно разносятся на
test / script / review-step (не всё машинно проверяемо — и это фиксируется).

Проверки верификатора:

- **A (тесты существуют):** каждое имя теста из колонки «Как проверить» со
  значением `test` резолвится reflection по тестовой сборке; иначе — падение
  с перечислением отсутствующих.
- **B (ADR покрыты):** заголовки `### ADR-\d+` из `docs/architecture/README.md`
  парсятся; каждая запись упомянута хотя бы в одной строке реестра (колонка
  «Первоисточник»).
- **C (уроки владельца покрыты):** каждый заголовок `##` в `lessons.md`,
  содержащий «правило владельца» или `Урок №\d+`, а также каждый номер
  `№\d+`, встречающийся в заголовках, упомянут в реестре (колонка
  «Первоисточник»).
- Нарушение формата таблицы — падение с внятным сообщением (простые регекспы,
  без markdown-парсера).

`VersionSyncTests`: одна каноническая строка версии сверяется по **девяти**
местам (csproj 1 + .iss 3 + INSTALL.md 3 + README 1 + CHANGELOG 1; ревью
R-2026-09-13-02, актуализация §12) — `<Version>` в `src/…csproj`;
`#define MyAppVersion`, `OutputBaseFilename` и шапочный комментарий (`v…`) в
`installer/*.iss`; INSTALL.md — имя сетапа (2 вхождения) и подвал
«Версия: …»; подвал README.md; секция `## [x.y.z]` в CHANGELOG.md.
Расхождение любого места — падение с диагностикой всех девяти значений.
Два макро-места .iss (`#define MyAppVersion` вычисляется через
`GetVersionNumbersString`, `OutputBaseFilename` подставляет макрос) литерала
версии не содержат — верификатор проверяет их структурно (шаблон строки
`SnowMeltingCalculator-v{#MyAppVersion}-Setup`, шапка-комментарий `v<канон>`),
остальные семь — точным совпадением канона.

**Критерий приёмки:** реестр покрывает ADR-001…014 и все правила владельца;
`RulesRegistryTests`, `VersionSyncTests` и полный набор зелёные (локально,
включая UiSmoke).

- **Не-цели:** автозапуск ревью (уровень 4), агрегация метрик по чекам
  (уровень 5). Формат только готовит данные (скрипт «находок на фазу» —
  будущая фаза, отдельное решение владельца).

**Критерий приёмки:** шаблон `review-receipt-template.md` создан по практике
четырёх чеков (поля + вектора атаки A1–A8); строка AGENTS.md про

без подсказок.

## 6. Owner-гейты

| Гейт | Что решает владелец | Когда |
|---|---|---|
| G1 | Аппрув актуализации → сигнал «делай» на остаток (фаза B + хвост C) | сейчас |
| G2 | Branch protection «только зелёный в master» | фаза A внедрена — решение за владельцем (настройка GitHub) |
| G3 | Приёмка результата каждой фазы (обычный handover) | по ходу |

Коммиты — только по явной команде владельца; до G1 дерево остаётся
некоммиченным.

## 7. Что не меняется

- Продукт, формат `.smc`, UI, state ownership, R1–R6, списки санкционированных
  writers — без изменений; ADR-запись не требуется (процессный слой вокруг
  кода), в handover каждой фазы фиксируется «state ownership без изменений».
- Замороженное досье `docs/architecture-migration/` — только чтение.
- Журнал ADR `docs/architecture/README.md` — без новых записей: находки
  ревью процессных планов живут в чеке ревью и §11 плана (процессный слой,
  не архитектура — ревью P3-9).
- Все существующие owner-гейты и ритуалы (план → ревью → show-me → реализация
  → handover) сохраняются как есть.

## 8. Риски и цена

| Риск | Оценка | Митигация |
|---|---|---|
| Флейки в CI (скрытые нестабильные тесты станут видимыми) | вероятны | флейк-политика (решение 12); видимость флейков — самоцель |
| Минуты windows-раннера | замер на прогоне 1 | при исчерпании — G2-обсуждение; ожидаемо в лимитах |
| Хрупкость markdown-парсинга в верификаторе | низкая для проверок A/B, средняя для C (текстовые якоря уроков) | простые регекспы, падение с внятной диагностикой; грамматика колонок зафиксирована в §4 |
| Бюрократия чеков «для галочки» | процессный | чек пишет независимый ревьюер; шаблон жёстко структурирован |
| UiSmoke вне CI — ложное чувство защиты | осознано | локальный полный прогон остаётся обязательным шагом handover (правило AGENTS.md) |

Накладная стоимость в установившемся режиме: строка реестра на новое
правило (~2 мин), чек на материальное ревью (~10 мин), ноль на обычный
коммит.

## 9. show-me

[show-me-process-gates.html](show-me-process-gates.html) — самодостаточный

## 10. Эффект

- Уровень 3 закрыт инфраструктурно: инварианты нельзя закоммитить сломанными

  материального ревью — перечитываемый след (чек).
