# План: партия правок «УГВ / шаблон / схема на Результатах»

Дата: 2026-09-04. Статус: план прошёл ревью (4 прохода, журнал в §6),
замечания внесены — ожидает утверждения владельцем. Решения утверждены
владельцем (выбор вариантов в диалоге), объём: ~6 файлов + правки
существующих тестов (см. 2.6), точечные правки, архитектура не меняется.
Изменение классифицируется как **material** (семантика состояния конструкции,
жизненный цикл сброса, трактовка persistence) → независимое read-only ревью
плана выполнено до реализации.

## 0. Исходные факты (подтверждены кодом и живым воспроизведением)

1. `ConstructionViewModel.ApplyTemplateCore` строит канонический снапшот из
   слоёв, созданных `ConstructionService.CreateFromTemplate` — а тот считает λ
   по `template.DefaultGroundwaterLevel` (у встроенных шаблонов 2.0), и
   подкладывает текущий УГВ проекта. При УГВ < 1 м снапшот получается
   самопротиворечивым (УГВ «влажный», λ — «сухие»), валидатор выдаёт
   предупреждение на каждый слой под трубой.
2. `MainViewModel.PerformNewCalculationReset` передаёт в
   `ConstructionDefaultStateInitializer.Apply` УГВ **текущего** проекта —
   новый расчёт наследует «влажные» условия. Тот же паттерн в
   `ProjectLoadOrchestrator.ResetModules` (там нейтрально: следом файл
   восстанавливает свой УГВ).
3. `ConstructionVisualizationView` в `ResultsView.xaml` привязан к
   `DataContext="{Binding ConstructionViewModel}"`, но у `ResultsViewModel`
   такого свойства нет → `_viewModel = null` → `DrawConstruction` не рисует
   ничего, видна пустая рамка («полоса»).
4. `ApplyLifecycleSnapshotToAdapter` обновляет `GroundwaterLevel`, но не
   `SelectedGroundwaterOption` → комбобокс УГВ может показывать «сухие
   условия» при фактических 0.5 м и сам «прыгает» при применении шаблона.
5. `ProjectLoadOrchestrator.BuildLayerSnapshots` жёстко восстанавливает
   `IsLambdaOverridden = false` → ручные λ теряются при первом же
   переключении УГВ после открытия проекта.
6. `ConstructionDefaultStateInitializer.CreateLayer` всегда пишет `LambdaA`,
   даже при УГВ < 1 м → «мокрый» новый расчёт встречает пользователя стеной
   λБ-предупреждений.

## 1. Утверждённые решения (owner)

- **D1. Новый расчёт** — всегда заводской УГВ 2.0 м («сухие условия»).
  Наследование УГВ из открытого проекта убирается.
- **D2. Применение шаблона** — шаблон задаёт только состав и толщины слоёв;
  λА/λБ всегда пересчитывается по текущему УГВ проекта. Превью шаблона
  считается по тем же правилам.
- **D3. Схема на «Результатах»** — чинится подключение к корректному
  источнику данных (однозначная поломка, варианта продукта не было).
- **D4. Комбобокс УГВ** — всегда отражает фактический `GroundwaterLevel`,
  не перепрыгивает сам.
- **D5. Ручные λ** — признак `IsLambdaOverridden` переживает сохранение и
  открытие проекта.
- **D6. Дефолтные слои** — считаются по фактическому (целевому) УГВ.

## 2. Изменения по файлам

### 2.1 `src/Services/Project/ConstructionDefaultStateInitializer.cs`

- Константа заводского УГВ `DefaultGroundwaterLevel = 2.0` (одно место,
  без магических чисел в вызывающих).
- `CreateLayer`: для слоёв `BelowPipe` λ = `GWL < 1 ? LambdaB : LambdaA`
  (семантика `Layer.UpdateLambda`), для `AbovePipe` — `LambdaA` (D6).
- Добавить перегрузку `Apply(origin)` без явного УГВ, использующую константу.
  Существующий `Apply(double, origin)` сохранить (используется тестами).

### 2.2 `src/ViewModels/Shell/MainViewModel.cs`

- `PerformNewCalculationReset`: вызывать `Apply(origin)` с заводским УГВ
  вместо `_constructionState.Snapshot.GroundwaterLevel` (D1).

### 2.3 `src/Services/Project/ProjectLoadOrchestrator.cs`

- `ResetModules`: заводы УГВ через ту же перегрузку (консистентность;
  поведение загрузки не меняется — файл восстанавливает свой УГВ).
- `BuildLayerSnapshots`: сохранять `layerData.IsLambdaOverridden` как есть
  (D5); пересчёт λ по УГВ — только для не-переопределённых слоёв под трубой
  (как сейчас). Путь сохранения проверен ревью и уже пишет флаг:
  `ConstructionPersistenceMapper.ToLayerProjectData` переносит
  `IsLambdaOverridden` (строка 56; поле в `LayerProjectData`,
  `ProjectData.cs:182`) — правка только на стороне загрузки.

### 2.4 `src/ViewModels/Construction/ConstructionViewModel.cs`

- `ApplyTemplateCore` (D2): после `CreateFromTemplate` задать
  `newConstruction.GroundwaterLevel = GroundwaterLevel` — сеттер
  `Construction.GroundwaterLevel` сам пересчитывает λ по всем слоям
  (`Construction.cs`, `UpdateLambdaForGroundwater`) — и только затем строить
  снапшот кандидата → снапшот самосогласован: λ соответствует
  `candidate.GroundwaterLevel`. Ручной цикл `UpdateLambda` не нужен.
  Присваивание `SelectedGroundwaterOption` из `ApplyTemplateCore` убрать:
  опцию синхронизирует общий хелпер (см. ниже), один писатель опции.
- `OnSelectedTemplateChanged` (D2): превью строится с тем же пересчётом под
  текущий УГВ — превью == результат применения.
- `OnSelectedGroundwaterOptionChanged`: добавить guard
  `if (_isResetting || _isRefreshing || _isSyncing) return;` (сейчас
  обработчик без ограждений — источник «прыжка» и снапа кастомного УГВ к
  0.5/2.0). `_isSyncing` обязателен: `ApplyTemplateCore` работает под ним,
  и без этого guard-а снап кастомного УГВ (0.8 → 0.5) остаётся
  (найдено ревью, §6).
- `ApplyLifecycleSnapshotToAdapter` (D4): синхронизировать
  `SelectedGroundwaterOption` из `snapshot.GroundwaterLevel` по порогу 1.0
  (внутри `_isRefreshing`, через общий хелпер маппинга). Комбобокс —
  двухпозиционный: для кастомных значений (например 0.8 м) показывает
  ближайшее состояние, скаляр УГВ остаётся каноническим и не снапится.

### 2.5 `src/Views/Results/ResultsView.xaml` (D3)

- Основной вариант (минимальная поверхность): привязка через
  `RelativeSource AncestorType=Window` к `DataContext.ConstructionViewModel`
  (DataContext окна — `MainViewModel`, у которого свойство есть).
  Изменения только в XAML, DI и поверхность VM не растут.
- Запасной вариант (если ревью предпочтёт): пробросить ссылку
  `ConstructionViewModel` в `ResultsViewModel` конструктором и оставить
  текущий binding. Ссылка — адаптер на адаптер, владение состоянием не
  меняется; проверить отсутствие цикла в DI.

### 2.6 Тесты (`tests/SnowMeltingCalculator.Tests/`)

- Новый расчёт: сброс даёт УГВ 2.0 и слои, λ которых согласована с 2.0 (D1+D6).
- Шаблон при УГВ 0.5: снапшот после применения имеет λБ под трубой; валидатор
  не выдаёт **послойных** λБ-предупреждений (D2). Общее информационное
  предупреждение «УГВ < 1 м → λБ» при УГВ < 1 остаётся всегда — так устроен
  `ConstructionValidator.ValidateLambdaForGroundwater` (строки 209–213),
  это не регресс.
- Кастомный УГВ (например 0.8 из файла): применение шаблона и синхронизация
  комбобокса не снапят скаляр ни в VM, ни в каноническом снапшоте (D2+D4,
  регресс-тест на дыру guard-а).
- Загрузка проекта: `IsLambdaOverridden` сохраняется round-trip; переключение
  УГВ не затирает переопределённые слои (D5).
- Синхронизация комбобокса: `ApplyLifecycleSnapshotToAdapter` выставляет
  опцию по порогу, не трогая скаляр УГВ (D4).
- Инвентаризация затрагиваемых существующих тестов (найдено ревью):
  - `ResultsViewModelOpenProjectTests` (~строки 1120, 1153) — P0-7
    закрепляет «значение λ сохраняется, флаг сбрасывается» как намеренное;
    обновить синхронно с 2.3, отмену P0-7 зафиксировать строкой в
    `docs/architecture/README.md`.
  - `ProjectLifecycleFlowCharacterizationTests` (~строка 172) — assert
    `IsLambdaOverridden == false` после загрузки; обновить аналогично.
  - `ConstructionStateLegacyStoreGuardTests` — строковый guard
    `CountOccurrences("CreateLayer(") == 8`: при добавлении хелперов в
    `ConstructionDefaultStateInitializer` счётчик не сломать.
- Существующие ArchitectureRulesTests остаются зелёными; владение состоянием
  не меняется.

## 3. Критерии приёмки (руками, по живому приложению)

1. УГВ «влажный» → применить любой встроенный шаблон: слои под трубой с λБ,
   **послойные** λБ-предупреждения исчезли (общее информационное
   предупреждение валидатора остаётся — это норма), R₂ согласован, превью
   совпадает с итогом.
2. Влажный проект → Файл → Новый → «Не сохранять»: комбобокс «УГВ >= 1 м»,
   УГВ = 2.0, дефолтные слои λА, ноль предупреждений.
3. Проект с ручной λ → сохранить → открыть: ручная λ на месте и не
   затирается переключением УГВ.
4. Открыть «влажный» проект: комбобокс показывает «< 1 м»; применение
   шаблона стрелку не двигает.
5. Вкладка «Результаты»: схема конструкции отрисована (как на
   «Конструкции», компактный бокс 190 px, окно глубины 1 м).

## 4. Риски / заметки для ревью

- Комбобокс двухпозиционный vs скалярный УГВ: после D4 показывается
  состояние по порогу; кастомный скаляр не снапится (guard в 2.4). Это
  осознанный компромисс, не новый баг.
- `template.DefaultGroundwaterLevel` декоративен. Решение владельца
  (2026-09-04, «спрятать»): поле в UI редактора шаблонов отсутствует
  (проверено — TemplateEditorView.xaml его никогда не показывал), в модели
  свойство помечено XML-комментарием как устаревшее и хранится в
  templates.json ради совместимости формата.
- Проводная совместимость `.smc`: формат не меняется; D5 лишь
  восстанавливает предполагаемое поведение уже существующего поля. Путь
  сохранения флаг уже пишет (п. 2.3), старые `.smc` без флага читаются как
  `false` — прежнее поведение.
- Точки входа `ConstructionViewModel.Initialize()` и `Reset()` сохраняют
  текущий УГВ VM — намеренно (D6 «фактический»): заводской УГВ получает
  только жизненный цикл «новый расчёт» / сброс перед загрузкой. Заводской
  2.0 при старте приложения приходит из дефолта поля `_groundwaterLevel`.
- `ResetModules` при отклонённом preflight оставит «Конструкцию» на
  дефолтах уже с заводским УГВ (раньше — с унаследованным): приемлемое
  изменение edge-case, зафиксировано здесь.

## 6. Журнал ревью плана (2026-09-04)

Четыре независимых read-only прохода по этому документу:

| Ревьюер | Основа | Вердикт | Главное |
|---|---|---|---|
| Momus (полная инструкция omo) | проверка ссылок, исполнимость, QA-сценарии, максимум 3 блокера | APPROVE | все ссылки подтверждены; «проверить запись флага» снято — уже пишется |
| Oracle (полная инструкция omo) | прагматичный минимализм, bottom line / effort / confidence | план готов, 1 дыра | guard обязан покрывать `_isSyncing`; effort Short, confidence high |
| Простой Momus (наивный промпт) | «найди все слабые места» | 8 замечаний | P0-7-тесты сломаются; критерий приёмки 1 неисполним в исходной формулировке; строковый guard `CreateLayer(` |
| Простой Oracle (наивный промпт) | «оцени как архитектор» | план готов + улучшения | сеттер `Construction.GroundwaterLevel` уже пересчитывает λ — упрощение D2; дублирование порога 1.0 |

Принятые в эту ревизию изменения: guard `+ _isSyncing` (2.4), один писатель
опции и упрощение D2 через сеттер модели (2.4), снят открытый вопрос
записи флага (2.3), инвентаризация красных тестов и строкового guard-а (2.6),
переформулирован критерий приёмки 1 (§3), зафиксированы семантика
`Initialize`/`Reset` и edge-case `ResetModules` (§4).

Дополнение после решения владельца «спрятать» (2026-09-04): поле
`template.DefaultGroundwaterLevel` в UI редактора шаблонов не показывается
(и не показывалось); свойство модели помечено как устаревшее, значение
хранится в templates.json ради совместимости. Вопрос закрыт.
- Владение состоянием и INV-правила не меняются: канонический владелец —
  `ProjectSessionConstructionState`; VM остаются адаптерами; Results не
  получает собственных входов конструкции.
