> Дата: 2026-09-18. Статус: **ожидает сигнала владельца**. Решения
> D1–D6 получены 2026-09-18 в диалоге по итогам трёхфронтальной ревизии
> (production-код / тесты / гигиена-и-релиз); находки зафиксированы в
> этом же плане, P0-находка печати проверена по коду
> (`ResultsViewModel.cs:1035-1066`). show-me:
> [show-me-hardening-roadmap.html](show-me-hardening-roadmap.html).
> Порядок волн (§1) предложен агентом по поручению владельца («предложи
> последовательность и обоснуй»); волны с широкими поверхностями и
> расчётным ядром проходят независимое атакующее ревью до имплементации
> (чек-лист в §9).

## 0. Суть

Архитектура здорова (R1–R6 с машинной проверкой, ~2300 тестов, CI, ADR).
Четыре системных слабых места лежат вокруг неё:

1. **Рантайм-дефекты**: печать PDF почти наверняка сломана на .NET 8
   (`Verb="print"` без `UseShellExecute=true` → Win32Exception всегда);
   гидравлика молча считается от невидимых допущений 35/30 °C; NaN-свойства
   гликоля подменяются соседними и текут в расчёт; `SupplySpacing_cm = 0`
   даёт Infinity.
2. **Наблюдаемость = ноль**: 79 catch-блоков (5 пустых, ~15 с одним
   `Debug.WriteLine`); ошибки save/load `.smc` видны только в Debug-выводе;
   логирования нет как класса — production-инцидент невоспроизводим.
3. **Константы-«источники истины» не являются источником**: литералы формул
   в `ThermalCalculator`/`CircuitsCalculator` при существующих
   `ThermalConstants`/`HydraulicsConstants`; Kv-значения в трёх копиях;
   лимит 320 мбар в ≥6 местах и 4 единицах; `(int)inputs.Mode` как
   температура поверхности.
4. **Репозиторий и релиз**: ~373 МБ закоммиченных бинарников и мусор в
   индексе при уже написанных правилах `.gitignore`; релиз — ручной ритуал
   (publish/ISCC описаны текстом в INSTALL.md, тегов `v*` и артефактов нет).

Плюс тестовые хвосты: ~90 % времени прогона — продовый `Task.Delay(3000)`;
4 копии хелпера, удаляющие настоящий `%APPDATA%`-settings.json; побитовый
golden-master пин.

## 1. Порядок волн и обоснование

| # | Волна | Почему здесь |
|---|-------|--------------|
| 1 | **Репо-хирургия** (filter-repo + LFS) | Единственная **необратимая** операция — делается первой, на минимальной дельте, под backup-бандлом. После неё вся дальнейшая работа идёт в чистом лёгком репо, а LFS-политика закреплена до появления новых бинарников. Код не трогается — риск для продукта нулевой |
| 2 | **Точечные баги** (печать-сервис, гварды) | Быстрые победы малой поверхностью: восстанавливается мёртвая фича (D1), закрываются Infinity/NaN-пути. Извлечение `PrintService` заодно начинает разгрузку гиганта `ResultsViewModel` |
| 3 | **Наблюдаемость** (локальный лог, перепись catch) | Широкая **механическая** поверхность (79 catch) — идёт отдельно от физики, чтобы диффы ревью не смешивались; диагностическая страховка готова до расчётного рефакторинга |
| 4 | **Физика в канон** (baseline → 1e-9, литералы → константы) | Сначала **калибруем страхующую сетку** (D6), затем переносим литералы под её защитой: иначе первый эквивалентный FP-реордер уронит 43 baseline-кейса посреди ревью. Материальная волна: ADR + атакующее ревью обязательны |
| 5 | **Отклик UI и тестов** (clock injection; опц. async-каскад) | Самый большой **поведенческий** риск — последним, при живых логах. Часть 5a (clock) дешёвая и снимает ~36 с прогона и класс гонок статусов; часть 5b (async-каскад гидравлики) — отдельная точка решения после 5a |
| 6 | **Хвосты гигиены тестов и конфига** | Мелочи, которые дешевле делать, когда фикстурная база и конфиг-политика устоялись |

Общие правила каждой волны: зелёные `dotnet build` + `dotnet test`
(+ `ArchitectureRulesTests`); handover-строка «state ownership без
изменений» (волна 4 — с ADR-016); wire-контракт `.smc` не меняется ни в
одной волне; волны не смешиваются в один дифф.

## 2. Волна 1 — репо-хирургия (чистка истории + Git LFS)

### 2.1. Пререквизиты и страховка

- `pip install git-filter-repo` (или standalone-скрипт) — на машине его нет.
- Чистое рабочее дерево, свежая ветка-бэкап не нужна — вместо неё:
  `git bundle create ../ace-pre-surgery-2026-09-18.bundle --all`
  (полная копия истории одним файлом; откат = клон из бандла).
- **Локальные копии ценного до чистки**: `Тест/*.smc` (пользовательские
  проекты) копируются в `D:\IA\ace-local-keep\Тест\` и возвращаются на диск
  как untracked. *Чек-лист подтверждения владельца перед стартом.*

вернуть `git remote add origin …` и force-push `--force --tags`
(D3: клонов нет). Теги `fase-*` переживают rewrite (пересчитываются).

(статусы января противоречат CHANGELOG 1.5.x, ссылки на несуществующий
`Work/`) — *подтвердить*; CHANGELOG остаётся единственным носителем статуса.

### 2.3. Git LFS (второй rewrite той же волны, bundle перед ним)

- `.gitattributes`: LFS — только документные бинарники:
  `docs/presentation/**`, `Презентация/**/*.pptx`, `Презентация/**/*.pdf`,
  `docs/architecture-migration/evidence/**/*.png`.
- **Исключения из LFS (обычный git): `src/**`, `tests/**`, `data/**`,
  `resources/**`** — шрифты ttf и картинки нужны при сборке: CI не тянет
  ни одного LFS-объекта (checkout без `lfs: true`), квота GitHub LFS
  не расходуется на прогоны CI.
- `git lfs migrate import --everything` по этим путям; после — сборка и
  полный тест локально, force-push, зелёный CI.

## 3. Волна 2 — точечные баги (печать-сервис + гварды)

### 3.1. Печать: новый сервис (D1)

- **Новые файлы** `src/Services/Printing/IPrintService.cs` +
  `PrintService.cs`:
  - `PrintPdf(string path)`: `ProcessStartInfo { FileName, Verb = "print",
    UseShellExecute = true, CreateNoWindow = true }`; `Process` в `using`;
    результат `PrintResult` (Success/Failure с сообщением) вместо
    исключения наружу.
  - `OpenPdf(string path)` (Verb = "open") — fallback: принтера нет/печать
    не удалась → пользователь может открыть PDF системным просмотрщиком.
    *Точка подтверждения: добавить кнопку/сообщение «Открыть PDF» в ветке
    отказа печати.*
  - Шов для тестов: конструктор принимает `Func<ProcessStartInfo, Process>`
    (дефолт `Process.Start`); юнит-тест пинит `UseShellExecute == true` и
    `Verb == "print"`, не запуская процесс.
- **`ResultsViewModel`**: inline-блок `:1035-1066` выпиливается; команда
  зовёт `IPrintService` через DI (зависимость VM → Service легальна, R4
  не задет); confirm-диалог `IDialogService.ShowPrintDialog` сохраняется;
  процесс не держит состояние — сервис без состояния, singleton.
- **Тесты**: fake `IPrintService` на команду печати (успех → «Документ
  отправлен на печать», отказ → «Ошибка печати: …»); reflection-пин
  `UseShellExecute`. **Принятое ограничение** (D1: принтера нет): реальный
  акт печати верифицируется вручную «диалог отправлен, исключения нет»;
  в UiSmoke печать не добавляется.

### 3.2. Гварды ввода гидравлики

- `SupplySpacing_cm <= 0` → ошибка валидации **до** расчёта
  (`HydraulicValidator`); пин «0/отрицательное → Error-статус расчёта,
  не Infinity» (сейчас `CircuitsCalculator.cs:35` делит без проверки).
- NaN-свойства гликоля: интерполяция вне физического диапазона перестаёт
  подменять соседнее значение молча (`GlycolDataService.cs:593`) — возврат
  NaN + явная ветка расчёта «свойства теплоносителя вне диапазона базы»:
  контур помечается ошибкой с текстом вместо тихого распространения NaN в
  скорость/потери/отчёт. *Точка подтверждения: Error vs предупреждение —
  предложение Error (честный степпер ADR-012 уже умеет).*
- Fallback-температуры 35/30 °C (`CircuitsViewModel.cs:633-643`):
  поведение сохраняется (гидравлика считается от допущений), но в
  `StatusMessage` появляется предупреждение «Тепловой результат
  недоступен — использованы допущения 35/30 °C».

Гейт: зелёный прогон; состояние владения и wire не меняются; handover-ревью
обычное (поверхность ~5 файлов — не материальная).

## 4. Волна 3 — наблюдаемость (локальный лог + перепись catch)

- **Новый** `src/Services/Logging/IAppLog.cs` +
  `RollingFileLogger.cs` — без внешних пакетов:
  - путь `%LOCALAPPDATA%\SnowMeltingCalculator\logs\app.log` (+ `app.1.log`,
    `app.2.log`); **ротация ≤ 3 файлов × 5 МБ (суммарно ≤ 15 МБ)** (D2;
    5 МБ — нижняя граница диапазона владельца, экономнее для диска);
  - потокобезопасно (один lock), уровни Info/Warn/Error, локальный
    timestamp со смещением, flush при каждой записи (объёмы малы);
  - телеметрия отсутствует by construction — файл только пишется на диск;
  - корень логов инъекционный (env-шов `SNOWCALC_LOG_DIR` или protected
    virtual Path) — тесты не пишут в реальный %LOCALAPPDATA%.
- DI: singleton `IAppLog` (первым в композиции, до undo-дневника).
- **Перепись catch-блоков (79)**: правило «глушить можно только с записью»:
  каждый catch → log(≥ Warn) с типом исключения и контекстом; 5 пустых
  упраздняются; 29 `Debug.WriteLine` заменяются на log. Поведение catch не
  меняется (кроме пунктов ниже).
- **Точки пользователя**:
  - `ProjectFileService` (save/load `.smc`): log Error + существующий
    StatusMessage (текст не меняется);
  - `AppSettings`: log Warn при битом/незаписываемом settings.json,
    поведение (дефолты) сохраняется;
  - `FittingsRepository`/`CollectorRepository`: log + **разовое
    предупреждение в UI** «Справочник загрузился не полностью (детали в
    логе)» — канал без зависимости репозитория от VM: через существующий
    shell-статус/сообщение приложения; точка дизайна на ревью волны
    (материальная — широкая поверхность → атакующее ревью до имплементации).
- **Тесты**: ротация (запись > 5 МБ → сдвиг, вытеснение старшего), запись
  из нескольких потоков, инъекция корня; снапшот-тест «79 catch ни один не
  молчаливый» — grep-скан в духе ArchitectureRules (лог-вызов или
  комментарий-оправдание в allowlist).

Гейт: зелёный; R1–R6 не задеты (логгер — Service, не writer канона);
handover «state ownership без изменений».

## 5. Волна 4 — физика в канон (после калибровки baseline)

### 5.1. Допуск baseline (D6)

- `RefactorBaseline/ThermalBaselineTests.cs:155-165` и
  `CircuitsBaselineTests.cs:178-198`: `Is.EqualTo` → относительный
  компаратор `WithinRelative(1e-9)` (NUnit `.Within` — абсолютный; для
  ожиданий ≈ 0 нужен custom `IEqualityComparer<double>`:
  `|a−b| ≤ 1e-9·max(|a|,|b|,1)`). Пин остаётся change-detector'ом, но
  перестаёт падать от FP-реордеров и окружения. `[Explicit]`-регенераторы
  сохраняются.

### 5.2. Перенос литералов (значения не меняются)

| Где | Что | Куда |
|-----|-----|------|
| `ThermalCalculator.cs:54` | α = 2.26/2.6 | `ThermalConstants.HeatTransferCoefficientA/B/C` (уже существуют) |
| `ThermalCalculator.cs:607+` | лимиты −60/+10/20–90/50–500 | единый источник (развязка дублей `ThermalConstants` ↔ `ValidationConstants`) |
| `ThermalCalculator.cs:90-99,487-499,300-376` | дубли формулы снеготаяния и D/E-коэффициентов | приватные методы/константы — одна копия |

нет».

Гейт: зелёный; state ownership без изменений; ADR-016 в журнале.

## 6. Волна 5 — отклик UI и тестов

### 6.1. Часть 5a — clock injection (сначала)

- `ResultsViewModel`: 10 сайтов `await Task.Delay(3000/5000)` (`:673`,
  `:702`, `:756`, `:787`, `:810`, `:839`, `:951`, `:966`, `:994`, `:1016`)
  → инъекция `IDelayScheduler` (прод: реальный таймер; тесты: мгновенный).
  Гонка «старая задержка гасит свежий статус» закрывается отменой: каждая
  операция держит свой `CancellationTokenSource`, новая отменяет предыдущую
  очистку.
- Эффект: −~36 c прогона (12 тестов по ~3 c из 39 c суммарных), удаление
  класса гонок `StatusMessage`. Behavioral-тесты правятся минимально
  (ожидания уже через UI-объекты).

### 6.2. Часть 5b — async-каскад гидравлики (точка решения владельца после 5a)

- `CircuitsViewModel.Calculate/CalculateAllCollectors` — синхронный UI-поток
  после каждого пересчёта тепла (`ThermalStateCoordinator.cs:155-187`).
  Вариант: `Task.Run` + маршалинг результата на UI. Риск выше (транзиентные
  состояния, честность степпера ADR-012, гонки с undo-гейтом) — отдельный
  мини-план + атакующее ревью, **только если** владелец подтвердит
  проблему отзывчивости на реальных проектах.

Гейт: зелёный; слайсы канона не трогаются; 5b — при запуске — материальное
ревью.
