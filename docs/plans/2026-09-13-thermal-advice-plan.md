## 1. Мотивация

- Валидатор говорит, *что сломано*, но не *что делать*: `ThermalResultValidator`
  честно констатирует «Расчётная температура обратки (−20.8 °C) отрицательна»
  или «Перепад 70.8 °C превышает 30», но пользователь остаётся один на один
  с подбором (`src/Services/Thermal/ThermalResultValidator.cs:32–53`).
- Паттерн аналогов (LoopCAD supplemental heat, исследование 2026-09-08): при
  выходе за лимиты программа сама предлагает варианты выхода. Для советов по
  обратке и ΔT все данные уже есть в `ThermalCalculationResult` — ничего
  считать заново не нужно. Совет по температуре поверхности исключён по итогам
  ревью (P0): t_пов в этой модели — **вход** расчёта
  (`ThermalCalculator.cs:411`), а не результат; сравнивать «расчётную t_пов»
  с целью нечем (§4).
- **Принцип:** советы — derived-слой *поверх* валидации. Ошибки гейтят расчёт
  и живут в shell (`ShellValidationMessage`), советы ничего не гейтят и живут
  у места лечения. Никакой замены валидации — только добавление слоя.

## 3. Архитектура

- **Модель:** `src/Models/Thermal/ThermalAdvice.cs` — sealed record:
  `Id` (string), `Severity` (`ThermalAdviceSeverity`: `Warning | Error`),
  `Message` (string, готовый к показу текст), `TargetStep` (существующий
  `NavigationTarget` из `src/Models/Navigation/NavigationTarget.cs`).
- **Сервис:** `src/Services/Thermal/IThermalAdviceService.cs` +
  `ThermalAdviceService.cs` — чистая функция
  `Build(ThermalCalculationResult result) → IReadOnlyList<ThermalAdvice>`;
  без состояния, ничего не пишет, не бросает (при реализации сигнатура
  сокращена: ни один совет v1 входы не читает — только результат).
  Числа лимитов — только из `ValidationConstants` / `ThermalConstants`,
  без литералов.
- **DI и конструирование:** регистрация
  `services.AddTransient<IThermalAdviceService, ThermalAdviceService>()`
  рядом с `ThermalResultValidator`
  (`src/Configuration/ServiceCollectionExtensions.cs:290`); в ctor

  `IThermalStateCoordinator? coordinator = null` (`ThermalViewModel.cs:399`):

  `ThermalResultValidator`; пересчитывается при каждом `Calculate`. VM —
  адаптер: канонического состояния не создаёт, советы derived от результата

  укладки» — тем же стилем

    `SurfaceTemperatureHint` (прецедент уже в вьюхе).

- **Культура:** тексты советов формируются через
  `string.Create(AppCulture.Culture, …)` — как `PowerSummary`
  (`ThermalViewModel.cs:328–332`); десятичный разделитель — запятая

## 4. Каталог советов v1

Физика направлений (проверена ревью, P1×2): `T_обратка = 2×T_средняя − T_подача`,
`ΔT = 2×(T_подача − T_средняя)`. Поэтому и для обратки, и для ΔT рычаги
одного направления: **уменьшить подачу** или **увеличить шаг** (шаг ↑ →
мощность ↑ → T_средняя ↑ → обратка ↑ и ΔT ↓). Увеличение подачи и уменьшение
мощности ведут в обратную сторону; концентрация гликоля на ΔT не влияет
(входит только в расход, `ThermalCalculator.cs:533–537`).

**Единая цель ориентира (отзыв владельца 2026-09-14 после демонстрации):**
граничные ориентиры (2×T_средняя для обратки, T_средняя + MaxDeltaT/2 для
ΔT) конфликтуют между собой и неустойчивы к округлению — владелец ходил
итерациями 50 → 45,9 → 38,0 («опять не попал»). Оба совета ведут к одной
цели — подача для **ΔT ≈ 15 К** (`T_средняя + 7,5`, канон
`RecommendedSupplyTemperature`): одна итерация снимает оба нарушения,
совет согласован с постоянным хинтом. 7,5 — не лимит, а половина целевого
перепада: константа `TargetDeltaT = 15.0` в сервисе.

| Id | Условие (якорь кода) | Severity | Основа текста совета | Переход (v2) |
|---|---|---|---|---|
| `RETURN_NEGATIVE` | `2×T_средняя − T_подача < 0` (`ThermalResultValidator.cs:32–38`) | Warning | «Обратка (X °C): уменьшите температуру подачи до ≈Y °C (для ΔT ≈ 15 К) или увеличьте шаг укладки», Y = T_средняя + 7,5 | — (v2) |
| `DELTAT_MAX` | `ΔT > ValidationConstants.MaxDeltaT (30 K)` (`ThermalResultValidator.cs:48–53`) | Warning | «Перепад (X K) превышает 30 K: уменьшите подачу до ≈Y °C (для ΔT ≈ 15 К) или увеличьте шаг укладки», Y — та же | — (v2) |
| хинты полей | те же условия, спроецированные на поля подачи/шага | — | короткие тексты у поля | — |

**Палитра советов — вариант B (выбор владельца 2026-09-14, show-me
`show-me-thermal-advice-palette.html`):** карточка тихая (белый фон, рамка
Gray.300, янтарная статусная полоса слева, заголовок Gray.800), хинты у
полей — бейджи «янтарь 12%, чёрный текст» (канон tokens.json
`status_semantics.warning`: «только статусные полосы и бейджи, никогда
декоративно»), severity обоих советов Warning; красным на зоне говорит
только shell (ошибки) и HeroKPI (бренд-градиент). Кнопки перехода — teal
(историческая формулировка: в тот же день убраны, см. §13).
Токен `Status.Warning.Background` (#1FFFB300, 12%) добавлен в канон
`Tokens.Colors.xaml` (первичный источник семантики —
`docs/design/brandbook-2026-application.md` §2.3, tracked; tokens.json —
вторичный, канон презентационного конвейера).

- **Совет по температуре поверхности исключён из v1** (находка ревью P0):
  t_пов — вход расчёта (`ThermalCalculator.cs:411`), в
  `ThermalCalculationResult` её нет; после реализации surface-temperature
  ввод и цель совпадают. Кандидат v2 — если появится наблюдаемый критерий
  дефицита (решение 6).
- Пустое состояние: нарушений нет → список пуст, карточка не рендерится
  (`Visibility` по `AdviceList.Count`), хинты скрываются.
- Финальные тексты — на фазе B (правка текста не меняет условий и направлений).

## 5. Фазы и критерии приёмки

### Фаза A — сервис + модель + DI + тесты

- Файлы: `ThermalAdvice.cs`, `ThermalAdviceSeverity.cs` (или вложенный enum),
  `IThermalAdviceService.cs`, `ThermalAdviceService.cs`,
  `ServiceCollectionExtensions.cs` (+1 строка).
- Тесты: `ThermalAdviceServiceTests` — табличный каталог ситуаций:
  подача 50 °C / средняя 14.6 °C → **оба** совета (`RETURN_NEGATIVE` +
  `DELTAT_MAX` — нарушения одновременны); подача 29.5 °C / средняя 14.6 °C →
  только `RETURN_NEGATIVE` (ΔT = 29.8 ≤ 30); подача 28 °C → пустой список;
  комбинации → устойчивый порядок. Сверка с `ThermalResultValidator` —
  по веткам обратки (< 0) и ΔT > 30; ветка валидатора «ΔT ≤ 0» не
  проецируется на совет (ранний возврат невалидного результата,
  `ThermalCalculator.cs:469–478`) — вне скоупа сверки (находка ревью P3).
- Критерий: полный набор зелёный; handover фиксирует «state ownership
  без изменений».

### Фаза B — UI

- Файлы: `ThermalViewModel.cs` (AdviceList + свойства хинтов),
  `ThermalView.xaml` (карточка + хинты). Обвязка перехода в `MainViewModel`
  реализовывалась (прецедент `HeaderCalculate`) и удалена решением
  владельца 2026-09-14 — советы v1 ведут на текущий шаг (§13).
- AutomationId: в XAML-контракт
  (`ThermalAutomationIdSelectorContractTests`) включается только статическая
  `ThermalAdviceCard` — item-советы генерируются `ItemsControl` в рантайме,
  XAML-парсер их не видит (находка ревью P2); `ThermalAdviceItem_N` /
  `ThermalAdviceGoTo_N` покрываются UiSmoke-сценарием фазы C.
- Критерий: ручной сценарий владельца (подача 50 °C, средняя 14.6 → карточка
  Error с **двумя** советами + хинт у поля подачи; уменьшение подачи →
  карточка гаснет) + полный набор зелёный, включая UiSmoke локально.
- **Зависимость от плана surface-temperature снята** (находка ревью P3):
  surface-temperature уже реализована в дереве (Manual-режимы,
  `OperatingMode.cs:38–57`, урок №24) — и именно она сделала «расчётную
  t_пов» ненаблюдаемой, что и закрыло совет 3 (P0). Фазы независимы.

### Фаза C — полировка

- Locale-тест форматирования чисел в текстах советов (en-US-подмена CurrentCulture);
- UiSmoke-сценарий: пустое состояние на чистом старте + сквозной «труба (keyboard-канал) →
  подача 90 °C → карточка с советом `DELTAT_MAX`» (кнопка перехода упоминалась в исходной
  формулировке — убрана решением владельца, §13; сценарий дополнительно пинует её
  отсутствие). Пин пует `DELTAT_MAX`,
  а не `RETURN_NEGATIVE` (уточнение при реализации, синхронизировано с ревью реализации
  P3-4): при входной валидации «подача ≥ 2×T_средняя» совет отрицательной обратки
  на дефолтных данных не гарантирован, а ΔT &gt; 30 K при подаче 90 °C и T_средняя &lt; 45 °C —
  гарантирован;
- короткий раздел в `docs/Руководство_пользователя.md` (подраздел теплового расчёта).

## 10. Эффект

- Пользователь получает ответ «что делать», а не только «что сломано» —
  закрывается разрыв между честной констатацией валидатора и LoopCAD-опытом.
- Валидация остаётся гейтом, советы — навигацией; расчётная честность не
  меняется ни на одно действие.
- Фундамент v2: apply-клик (через канонических writers), гидравлические советы,
  бейдж shell.

## 11. Журнал ревью плана

Независимое read-only ревью в атакующем режиме (2026-09-13, чистый контекст
subagent): **REJECT** — 1 P0, 3 P1, 4 P2, 3 P3. Чек:
[docs/reviews/2026-09-13-thermal-advice-plan-review.md](../reviews/2026-09-13-thermal-advice-plan-review.md).
Все находки внесены в этот же дифф, show-me регенерирован (урок №27):

- **P0-1** совет `SURFACE_ABOVE_TARGET` нереализуем: «расчётной t_пов» нет в
  `ThermalCalculationResult` — t_пов является входом расчёта
  (`ThermalCalculator.cs:411`); show-me демонстрировал несуществующую
  величину → совет исключён из каталога v1 (§4), тезис §1 и решение 6
  скорректированы, решение 5 — 2 совета.
- **P1-2** `RETURN_NEGATIVE`: направление лечения перевёрнуто («увеличьте
  подачу до ≈29.2» при подаче 50; унаследовано от старого текста
  Планируемых_изменений п.1) → «уменьшите подачу до ≈2×T_средняя или
  увеличьте шаг» (§4).
- **P1-3** `DELTAT_MAX`: «увеличьте подачу» и «уменьшите нагрузку» ведут
  в обратную сторону (ΔT = 2×(T_подача − T_средняя)), «проверьте гликоль»
  фиктивен (гликоль — только в расходе) → «уменьшите подачу
  (≈T_средняя + 15 K) или увеличьте шаг»; гликоль убран (§4).
- **P1-4** навигация через `CurrentNavigationTarget` невозможна — сеттер
  приватный (`MainViewModel.cs:123–127`) → механизм по прецеденту
  `HeaderCalculate`: поиск MenuItem по Target → `SelectedMenuItem`;
  обвязка добавлена в файл-лист фазы B (§3, §5).
- **P2-5** show-me противоречил плану в направлении рычага «шаг»

## 13. Отзыв владельца на демонстрацию (2026-09-14)

Демонстрация на реальных данных (подача 50, T_средняя 23,0) показала слабость
граничных ориентиров: совет RETURN_NEGATIVE вёл к «≈45,9 °C» (=2×T_средняя,
обратка ровно 0), совет DELTAT_MAX — к «≈38,0 °C» (=T_средняя+15, ΔT ровно
30) — ориентиры конфликтовали, владелец ходил итерациями («опять не попал»),
ввод точного ориентира мог оставаться на границе нарушения из-за округления.
При этом прежний постоянный хинт «Рекомендуется: … (для ΔT ≈ 15 К)» владелец
оценил как рабочий («вводил — всё работало»).

Решение владельца (выбор из трёх вариантов, 2026-09-14): **единая цель
«для ΔT ≈ 15 К»** — оба совета ведут к подаче `T_средняя + 7,5`, одна
итерация снимает оба нарушения, совет согласован с постоянным хинтом
(решение №8, вариант A, работает как задумано: хинт скрыт, пока активны
советы, и возвращается с той же цифрой после их устранения).

Внесено: тексты советов (§4), тесты каталога (22,1 вместо 29,2 + тест
общего ориентира), руководство 6.8, show-me. Условия срабатывания советов
не менялись.

**Решение №8 подтверждено владельцем 2026-09-14 (G2): вариант A остаётся**
— при активных советах постоянный хинт «Рекомендуется: …» скрыт, его роль
играет совет с той же целевой цифрой; после устранения нарушений хинт
возвращается. Открытых owner-решений по плану не осталось.

**Палитра — вариант B подтверждён владельцем 2026-09-14** (выбор по
show-me `show-me-thermal-advice-palette.html`, см. §4): тихая карточка +
янтарные бейджи, severity Warning. Попутное решение владельца: курсив в
подписях приложения сохраняется (бренд-запрет курсива на WPF-приложение
не распространяется — «идеально вписывается»).

**Кнопки перехода убраны (владелец, 2026-09-14, после демонстрации B):**
оба совета v1 ведут на текущий шаг — кнопка «Перейти: …» не даёт перехода.
Из карточки убрана кнопка, из `MainViewModel` — команда `NavigateToTarget`
(мёртвый код недопустим); UiSmoke пинует *отсутствие* кнопки. Поля
`TargetStep`/`TargetTitle` в модели сохранены — оживут в v2, когда появятся
советы на чужие шаги (кандидат v2 вместо перехода — кнопка «Применить
ориентир ≈T_подачи», требует пересмотра решения №3).
