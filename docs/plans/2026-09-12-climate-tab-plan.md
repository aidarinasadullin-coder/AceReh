# План (единый): вкладка «Климат» — две задачи

> Дата: 2026-09-12. Статус: на приёмке владельца; реализация — только после
> owner-signal. Дерево не коммитится.
> Объединяет планы «wind-max-jan» и «climate-zone-checkbox» (2026-09-12,
> решения владельца зафиксированы в обеих сессиях; частные планы заменены
> этим документом и их show-me — одним общим).
> show-me: [show-me-climate-tab.html](show-me-climate-tab.html).

Две задачи одной вкладки, одна ветка, один независимый ревью, один handover,
одна версия:

- **Задача A — источник скорости ветра v_H**: переход с «средняя скорость
  ветра за период ≤ 8 °С» на «максимальная из средних скоростей по румбам
  за январь» (`wind_max_jan` из климатической базы).
- **Задача B — чекбокс «Повышенные требования» и зона**: список зоны
  убирается («мёртвый» контрол), чекбокс становится ступенью вниз от
  автоматики города, зона становится производной итоговой температуры,
  смена города сбрасывает чекбокс.

Порядок реализации: **A → B** (A локальна и не конфликтует с правками B;
пересечение поверхностей — `ProjectSessionClimateState`, `ClimateView.xaml`,
климат-тесты — правится в одну волну).

## Часть A. Скорость ветра: v_H → максимум из средних по румбам за январь

### A.1 Мотивация

В расчёте теплоотдачи α = 2,26·(tП − tH)^0,33 + 2,6·vH величина vH сейчас
берётся из климатической базы как «средняя скорость ветра за период со
средней суточной температурой ≤ 8 °С» (Майкоп: 3,1 м/с). Требуется источник
«максимальная из средних скоростей ветра по румбам за январь» (Майкоп:
5,4 м/с) — консервативная оценка конвективных потерь.

**Ключевой факт исследования:** данные уже лежат в `data/climate_db.json` —
поле `wind_max_jan` (совпадает с ожиданием владельца). JSON-модель
репозитория его уже читает (`Wind_Max_Jan`), в доменную модель не
прокидывается. Диапазон по базе 1,3–14,6 м/с (в валидацию 0,1–30
укладывается); заполнено у 547 из 550 городов; `null` у трёх: Мариуполь,
Запорожье, Аскания-Нова.

### A.2 Зафиксированные решения владельца (2026-09-12)

|---|---|---|

| A2 | Дефолт 5,0 м/с до выбора города (`ClimateParameters.WindSpeed`) | **Оставить** |

### A.6 Эффекты и риски

- vH↑ → α↑ → требуемая мощность↑ (Майкоп: Δα = 2,6·(5,4−3,1) ≈ +6,0 Вт/м²·К)
  — это цель изменения; отразить в CHANGELOG.
- 0 у трёх городов: подсветка валидацией (min 0.1), расчёт при 0 не падает —
  осознанное решение владельца.
- Смешение семантики у существующих проектов: значение в .smc — сохранённое;
  пересчёт старых проектов не форсируется; «Сбросить к данным города»
  подставит новое значение — ожидаемо.

## Часть B. Чекбокс «Повышенные требования» — ступень вниз; зона без списка

### B.1 Контекст и проблема

1. **Выпадающий список «Климатическая зона» — «мёртвый» контрол.**
   `ComboBox` двусторонне привязан к `ClimateViewModel.SelectedZone`
   (`src/Views/Climate/ClimateView.xaml:92`), но у свойства нет
   `OnSelectedZoneChanged` — выбор не публикуется в каноническое состояние и
   затирается зеркалом снимка при следующей правке
   (`src/ViewModels/Climate/ClimateViewModel.cs`, `MirrorSnapshot`).
2. **Каноническая зона всегда автоматическая** по пятидневке
   (`ProjectSessionClimateState.DetermineZone`): ≥ −27 → M10; −37 < t < −27 →
   M15; ≤ −37 → M20; чекбокс принудительно даёт M20_Plus.
3. **Чекбокс «Повышенные требования (колонка −20°C)»** ставит M20_Plus и, при
   выбранном городе, температуру **всегда ровно −20**, независимо от города.
4. Расчёт зону не использует (`ThermalCalculator` считает от `AirTemperature`);
   зона нужна для .smc, строки в PDF и отображения.
5. Одно значение представлено тремя контролами (список, чекбокс, строка
   «Зона:»), из которых работает один. PDF печатает сырое имя enum
   (`Zone_M15`).

### B.2 Решение и зафиксированные решения владельца (2026-09-12)

**Убрать список зоны; чекбокс — ступень вниз от автоматики города; зона —
производная итоговой температуры; смена города сбрасывает чекбокс.**

| # | Вопрос | Решение |
|---|---|---|
| B1 | От чего считать ступень | **От автоматики города** (температура, которую город дал по пятидневке). Клик по чекбоксу всегда перезаписывает температуру значением «автоматика + ступень» |
| B2 | Шкала ступени | −10 → −15; −15 → −20; при автоматике −20 чекбокс **неактивен** (`IsEnabled=false`) |
| B3 | Снятие чекбокса | Возврат к автоматике города (сегодняшнее симметричное поведение сохраняется) |
| B4 | Зона при чекбоксе | **Зона = дискретизация итоговой температуры** (−10 → M10, −15 → M15, ≤ −20 → M20). M20_Plus больше не порождается — legacy для старых .smc |
| B5 | **Смена города** | **Чекбокс сбрасывается**: новый город всегда начинается с чистой автоматики (решение владельца 2026-09-12, уточнение к ранее рассмотренной версии «флаг сохраняется») |

### B.3 Таблица правил (целевое поведение)

| Пятидневка t₅ | Автоматика (чекбокс выкл) | Чекбокс вкл | Чекбокс при t₅ |
|---|---|---|---|
| ≥ −27 | −10 °C, M10 | −15 °C, M15 | активен |
| −27 < t₅ < −37 | −15 °C, M15 | −20 °C, M20 | активен |
| ≤ −37 | −20 °C, M20 | — | **неактивен** |

- **Смена города → чекбокс сбрасывается**, итог = чистая автоматика нового
  города (B5). «Сбросить к данным города» — тоже чистая автоматика, флаг
  сбрасывается.
- Зона при **ручной** правке температуры: ближайшая колонка {−10, −15, −20}
  (границы −12.5 / −17.5; tie — холодная сторона). PDF и строка «Зона:»
  всегда согласованы с температурой.
- Без выбранного города чекбокс неактивен (тултип «Выберите город»).
- Undo/Redo: без новых механизмов — существующие мутации через
  `ApplyIndividualEdit` / `ApplyCitySelection` (origin User) → `Changed` →
  дневник ADR-014; откат — существующий `ApplySnapshot`. Смена города — одна
  мутация (город + климат + сброс флага) = одна запись дневника.

Тексты UI:

- Чекбокс: `Повышенные требования (ступень вниз: −10 → −15, −15 → −20)`;
  тултип: «Применить следующую, более холодную колонку таблицы мощности
  поверх данных города. Сбрасывается при смене города. При расчётной
  температуре −20 °C недоступен.»
- Неактивный чекбокс при t₅ ≤ −37: «Город уже в зоне −20 °C — ступень не требуется».
- Строка «Зона:» (приглушённая) остаётся: формат `M15 · колонка −15 °C`.

## Общее для обеих задач

### Пересечение поверхностей (правится в одну волну)

- `ProjectSessionClimateState`: A — 2 точки ветра; B — логика зоны/чекбокса.
- `ClimateView.xaml`: A — тултип ветра; B — удаление списка зоны, чекбокс.
- Тесты `ClimateStateTests`, `ClimateViewModelTests`,
  `ClimateMultiplicityCharacterizationTests` — обе части.

### Инварианты (не меняется)

- **State ownership**: канонический писатель климата —
  `ProjectSessionClimateState`, санкционированные писатели не расширяются
  (существующие мутации). R1–R6 целы, `ArchitectureRulesTests` не правится.
- **Persistence**: .smc wire без изменений в обеих частях → ADR не требуется.
- Формула α и `ThermalCalculator`, гидравлика (ветер не использует),
  каскад инвалидации Climate → Thermal → Results, Undo/Redo-механика.
- **Results** — derived; зона/ветер в PDF — отображение.

### Версия и релиз (правило №20)

1.2.0 → **1.3.0**: пользовательски заметные изменения вкладки «Климат»
(источник ветра — рост расчётных мощностей; новое поведение чекбокса).
Синхронно: `csproj` (первоисточник `<Version>`), `.iss` (комментарий,
`MyAppVersion`, `OutputBaseFilename`), `INSTALL.md` (имя сетапа ×2, подвал),
`README.md` (подвал), `CHANGELOG` ([1.3.0]: ветер → wind_max_jan; ступень
повышенных требований; зона без списка; PDF-формат зоны). Проверка: grep
1.2.0 в декларирующих файлах — 0 вхождений.

### Процесс

- Материальное изменение по поверхности (≈25 файлов с тестами) → один
  независимый read-only ревью диффа перед коммитом; находки — в handover
  (и в `docs/architecture/README.md`, если меняют дизайн).
- Гейты: приёмка плана владельцем (открыть show-me, урок №21) → owner-signal
  «делай» → реализация A → B → полный зелёный `dotnet test` → handover
  некоммиченным деревом. Коммит — по явной команде владельца.
- Ручная приёмка: Майкоп в «Климате» → ветер 5,4; чекбокс для Майкопа:
  −10 → −15 (M15); Казань: −15 → −20 (M20); Красноярск: чекбокс неактивен;
  смена города сбрасывает чекбокс; PDF: «M15 · колонка −15 °C» и ветер 5,4.

### Урок (кандидат в `docs/agents/lessons.md`)

TwoWay-биндинг без обработчика изменения — мёртвый контрол: каждый UI-вход
должен публиковаться в каноническое состояние; проверять при ревью UI.

### Вне скоупа

- Ручной выбор произвольной зоны из списка (варианты B/C обсуждения
  2026-09-12) — отклонён владельцем в пользу варианта A со ступенью.
- Переписывание `data/climate_db.json`, замена данных трёх городов без
  `wind_max_jan`.
- Изменение `.smc` wire, списков санкционированных писателей, ADR.
