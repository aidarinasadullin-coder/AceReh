**Дата:** 2026-09-06. **Статус:** план к выполнению по явной команде владельца.
**Спецификация:** `docs/report-spec-v2.md` (принята).
**База:** отчёт v1 (`src/Services/Reports/Calculation/`), краткий PDF
(`src/Services/Results/`) — не изменяются.

## 0. Предусловия и координация с параллельными работами

### 0.1 Рефакторинг больших файлов (перед реализацией; sess_806fb23e)

Владелец перед генерацией проведёт decomposition-дробление больших файлов
(домены и порядок — по sess_806fb23e): **ResultsViewModel — первый** (1854
строки, hotspot №1), затем Hydraulics; `ThermalCalculator`, `MainWindow.xaml`,
`Services/Reports/**` в дробление не входят. Следствия для этого плана:

- **Якоря — только по символам, не по строкам.** Ссылки вида
  `ThermalCalculator.cs:20-55`, `ResultsViewModel.cs:704` в этом плане и
  спецификации — индикативны на 2026-09-06. Перед каждым этапом — сверка
  якорей по символам (grep имени класса/метода/свойства); если символ
  переехал в новый файл после дробления — работать по новому адресу, план
  не править (адрес — не контракт).
- **R2 спроектирован так, чтобы пережить дробление Results**: экспортный
  сервис получает данные напрямую из `ProjectSession` (канонические снимки),
  а не через `SaveCurrentProject()`/`ResultsViewModel`; команда UI — тонкий
  релей, который после дробления просто живёт в новой под-VM (совпадает с
  рекомендацией sess_806fb23e: генератор — отдельный сервис, НЕ через
  ResultsViewModel).
- R6 (MainWindow.xaml) от рефакторинга не зависит — файл признан здоровым.
- Тестовые файлы (`ResultsViewModelOpenProjectTests` и т.п.) могут
  переименовываться — T2-регрессия ссылается на поведение, не на имена
  тест-классов.

## 1. Этапы

### R0. Фиксация документов (docs-only, отдельный коммит)

### R1. Константы расчётного ядра (S; ревью: расширен)
- Тепло: в `src/Core/Constants/ThermalConstants.cs` все 8 констант уже
  объявлены публично с идентичными значениями, но `ThermalCalculator` их не
  использует. R1: переключить `ThermalCalculator` на `ThermalConstants`,
  удалить дубль-литералы (ThermalCalculator.cs:20-55); значения не меняются,
  T2-01 подтверждает неизменность расчёта. **Запрет**: константы
  `ThermalConstants.SurfaceTemp*` (2/0/−2) не использовать как источник
  температуры поверхности — фактическая логика `(int)inputs.Mode` = 3/5/7.
- Гидравлика — карта «величина → единственный источник» (ревью P2):
  лимиты оборотов — `ValveTurnsCalculator.GetMaxTurns`; Kv клапанов —
  `ValveTurnsCalculator.KV_*`; границы Re/шероховатость —
  `FlowRegimeCalculator` (публичные); лимиты v/R/Δp/ΔT —
  `ValidationConstants` + `CircuitTemperatureResult.MaxPressureLossPerMeter`;
  коэффициенты формул Dp — литералы `CircuitsCalculator` (раскрыть в
  константы или ссылаться при совпадении значений). **`HydraulicsConstants`
  не использовать без построчной сверки** — значения расходятся с кодом
  (MaxTurns_HKV_D=4 vs 2.5; MinVelocity=0.5 vs 0.1).
- Тесты T2-01.

### R2. Источник данных: каноника + контрольный пересчёт (S/M)
- Новый `ThermalReportDataProvider` (рядом с `Services/Reports/Calculation/`).
  Спроектирован независимым от `ResultsViewModel` и его будущего дробления
  (§0.1): данные — напрямую из `ProjectSession`, не через
  `SaveCurrentProject()`:
  1. читает `ProjectSession.ThermalState.Snapshot`;
  2. если расширенные величины нулевые — ровно один
     `ThermalCalculator.Calculate(inputs, climate, construction)` по данным
     проекта; результат никуда не пишется;
  3. **сборка входов пересчёта — ровно как `ThermalViewModel.BuildThermalInputs`
     (ревью P2)**: Mode/Supply/Ground/Pipe (`ToPipeType()`)/PipeSpacing из
     `ThermalState.Snapshot.Inputs`, LambdaE из
     `ConstructionState.CurrentProjection`, cp/ρ — **дефолты `ThermalInputs`**
     (1053/3.39, как в основном пайплайне); иначе ложные расхождения со
     сверкой и конфликты расходов между разделами 5 и 6; у расходов
     пересчёта — пометка о дефолтном теплоносителе;
  4. сверка PowerUp/PowerTotal/ΔT пересчёта с сохранёнными 8 полями →
     примечание при расхождении;
  5. предикат REPORT_INPUTS_STALE (ревью P2):
     `ThermalState.Snapshot.Status.Phase == NeedsRecalculation` **и**
     `Result != null` (не общий `IsDirty`); успешный fallback-пересчёт по
     текущим входам исключает stale (upstream-инвалидация даёт отчёт из
     пересчёта без противоречивого предупреждения);
  6. пересчёт вернул `IsValid=false` → шаги «нет данных» +
     MISSING_THERMAL_DETAIL + `ValidationErrors` пересчёта в «Проверки»;
  7. флаг источника (снимок/пересчёт) в данных отчёта.
- Точка стыковки: `ICalculationReportExportService.ExportReportAsync`
  дополнительно принимает провайдер/снимок **и `reportDate`** (сейчас дата не
  передаётся — в заголовке 0001-01-01); команда UI — **тонкий релей**:
  только передаёт сессию/дату в сервис (сейчас передаёт `SaveCurrentProject()`
  — `ResultsViewModel.cs:704`, после дробления релей живёт в новой под-VM,
  якорь по символу метода экспорта, не по файлу); DI
  (`ServiceCollectionExtensions`).
- Правка в команде экспорта точечная — сигнатура вызова, не логика.
- Тесты T2-02…T2-05, T2-07.

### R4. Билдеры секций (M)
- `ThermalSectionBuilder`: реальные значения из провайдера R2 (нули исчезают);
  шаги α → Qтаяния → Qконв → PowerUp → RFb → m → ηR (+A–E таблицей) → JHmü →
  Tсредняя → Tобратки/ΔT → qD → qTotal → расходы; константы — из R1;
  формулы — существующие привязки (`ThermalCalculator.cs:*`).
- `ConstructionSectionBuilder`: правило λА/λБ по УГВ; R1/R2 с подстановкой
  по слоям.
- `ClimateSectionBuilder`: пометки источников (пользователь / база программы /
  данные СП).
- `HydraulicsSectionBuilder`: референсный контур (В4) — цепочка шагов из
  **сохранённых** полей контура (Q_HK, V̇, v, Re, λ, R, Dp…); tie-break при
  равных DpGesamt — минимальный номер контура (совместимо с доменным
  `IsReferenceCircuit`, ревью P3); пример балансировки (Δp дросселя →
  обороты, правило вычитания HKV-D/IV; Kv-формула без подстановки с пометкой
  «Kv контура не сохраняется»); подбор коллектора; примечание о семантике
  DpVent; missing-data выбранного режима → маркер + предупреждение (T2-13).
- Статусы формул билдеров (ревью P3): пометки «требуется привязка к
  существующей формуле» у PowerDown/ExcessTemperature и в гидравлике
  заменить реальными привязками — формулы уже есть в списках билдеров;
  в v2 старые статусы не протекают.
- Тесты T2-06, T2-10, T2-13.

## 2. Правила процесса

- Коммиты: R0 отдельно (docs); каждый этап — отдельный коммит с зелёным
  тест-подмножеством; без Owner-review не мержится (правила AGENTS.md).
- Независимый read-only обзор: **план** отревьюирован 2026-09-06 (два
  агента: сверка с кодом; правила/спецификации; вердикты «готов с правками»,
  правки внесены). Для реализации: обзор отчётной модели R1–R4 выполняется
  до R5 (поверхность широкая — формально material по AGENTS.md независимо от
  persistence; state ownership/persistence не затрагиваются — фиксируется
  ADR-010). Обзор включает R1 (раскрытие констант расчётного ядра).
- Запрещено: новые расчётные модули; формулы не из кода/документации;
  новые warning-пороги; изменения `.smc`, краткого PDF, канонического домена.
