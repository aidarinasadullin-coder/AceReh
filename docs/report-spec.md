# Спецификация детального расчётного отчёта

## 1. Назначение

Документ описывает новый экспорт детального расчётного отчёта для WPF-приложения SnowMeltingCalculator.

Новый отчёт предназначен для передачи заказчику как инженерный расчётный документ. Он должен показывать исходные данные проекта, выбранные пользователем параметры, значения из справочников программы, расчётные результаты, формулы, предупреждения и трассировку источников данных.

Существующий PDF-экспорт сохраняется как краткий отчёт "Результат". Новый детальный отчёт не заменяет существующий экспорт и реализуется отдельным экспортным сценарием.

## 2. Продуктовые решения

| Решение | Требование |
| --- | --- |
| Существующий PDF сохраняется | Текущий экспорт через `ResultsPdfData`, `ResultsPdfDataBuilder`, `PdfExportService` остаётся кратким отчётом результатов. |
| Новый отчёт отдельный | Детальный расчётный отчёт получает отдельную команду, модель данных, builder и renderer. |
| Назначение | Документ используется для передачи заказчику и инженерной проверки расчёта. |
| Стиль MVP | Нейтральный инженерный документ: заголовки, таблицы, единицы измерения, предупреждения, приложения. Без маркетингового/дашбордного оформления. |
| Методика | Расчёт описывается как выполненный по внутренней методике REHAU, уже представленной в коде и документации приложения. |
| Нормативные заявления | Нельзя заявлять соответствие ГОСТ/СП, если конкретный источник данных явно не содержит такую ссылку. |
| Расчёты | В MVP запрещено добавлять новые расчётные модули ради отчёта. Все численные значения берутся из состояния программы/проекта. |
| Режимы | Детальный отчёт формируется отдельно для рабочего режима и отдельно для расчётного/холодного режима. |
| Трассировка | В MVP у отображаемых значений должен быть источник: ввод пользователя, проект, база программы, расчёт программы или производное значение. |
| Предупреждения | Предупреждения строятся только на существующих данных проекта, флагах, лимитах и проверках программы. Пороги нельзя придумывать в отчёте. |
| Формулы | Формулы показываются один раз в разделе или приложении, затем приводятся таблицы результатов. Подстановки для каждого контура в MVP не нужны. |

## 3. Связь с существующим экспортом

### 3.1 Краткий отчёт "Результат"

Текущий PDF-экспорт остаётся кратким отчётом/дашбордом результатов.

Существующие файлы:

| Файл | Роль |
| --- | --- |
| `src/Services/Results/ResultsPdfData.cs` | DTO для краткого PDF-отчёта. |
| `src/Services/Results/ResultsPdfDataBuilder.cs` | Сборка данных краткого PDF из текущего состояния результатов. |
| `src/Services/Results/PdfExportService.cs` | Рендер краткого PDF через QuestPDF. |
| `src/Services/Results/IPdfExportService.cs` | Интерфейс существующего PDF-экспорта. |

Поведение существующего экспорта должно остаться неизменным. Допустимое изменение UI: добавить рядом отдельную команду для нового детального отчёта.

### 3.2 Детальный расчётный отчёт

Новый отчёт реализуется отдельным путём:

```text
Текущее состояние проекта/программы
    -> CalculationReportDataBuilder(reportMode)
    -> CalculationReportData
    -> CalculationReportMarkdownRenderer
    -> .md

Текущее состояние проекта/программы
    -> CalculationReportDataBuilder(reportMode)
    -> CalculationReportData
    -> CalculationReportPdfRenderer
    -> .pdf
```

Markdown нужен как проверяемый промежуточный/технический формат и как удобная форма контроля полноты. PDF нужен как официальный файл для передачи заказчику.

## 4. Цели

| ID | Цель |
| --- | --- |
| G-1 | Сформировать детальный инженерный расчётный отчёт для передачи заказчику. |
| G-2 | Сохранить существующий краткий PDF-отчёт как отдельный экспорт "Результат". |
| G-3 | Поддержать отдельную генерацию отчёта для рабочего и расчётного/холодного режима. |
| G-4 | Добавить трассировку источников значений в MVP. |
| G-5 | Использовать только существующие значения из программы и проекта. |
| G-6 | Показывать предупреждения только на базе существующих данных, проверок и лимитов. |
| G-7 | Использовать единую модель отчёта для Markdown и PDF. |
| G-8 | Сделать builder и renderer тестируемыми независимо от WPF-визуального слоя. |

## 5. Не цели

| ID | Не цель | Причина |
| --- | --- | --- |
| NG-1 | Не заменять `.smc`. | `.smc` остаётся форматом проекта, а отчёт является экспортным артефактом. |
| NG-2 | Не заменять существующий краткий PDF. | Краткий "Результат" и детальный протокол решают разные задачи. |
| NG-3 | Не добавлять новые инженерные расчёты в MVP. | Отчёт должен отражать расчёт программы, а не считать независимо. |
| NG-4 | Не позволять отчёту или агенту рассчитывать значения. | Все численные данные должны быть произведены приложением. |
| NG-5 | Не придумывать формулы. | Формулы берутся только из существующего кода и документации. |
| NG-6 | Не заявлять ГОСТ/СП-соответствие без явного источника. | Отчёт основан на внутренней методике REHAU. |
| NG-7 | Не повторять старый `README v.2.1.md` буквально. | Старый файл используется как пример полноты и терминологии, не как обязательный шаблон. |
| NG-8 | Не делать подстановку формулы для каждого контура в MVP. | Формула один раз плюс таблицы результатов достаточно для инженерной проверки. |
| NG-9 | Не придумывать новые warning-пороги. | Предупреждения должны иметь источник в коде, проекте или базе программы. |

## 6. Режимы отчёта

Детальный отчёт всегда формируется для одного выбранного режима.

| Режим | Источник данных контуров | Назначение |
| --- | --- | --- |
| `Operating` | `OperatingResult` у контура | Протокол рабочего режима. |
| `DesignCold` | `DesignResult` у контура | Протокол расчётного/холодного режима. |

Builder детального отчёта должен принимать параметр режима. Он не должен безусловно использовать `OperatingResult`, как это сейчас делает builder краткого PDF.

Если для выбранного режима у контура нет результата, отчёт должен:

1. Показать стабильный маркер отсутствия данных, например `нет данных`.
2. Добавить предупреждение с указанием коллектора/контура и выбранного режима.
3. Не пытаться пересчитать значение внутри отчёта.

## 7. Трассировка источников

### 7.1 Категории источников

| Категория | Значение |
| --- | --- |
| `UserInput` | Значение введено или выбрано пользователем. |
| `Project` | Значение хранится в проекте или структуре текущего проекта. |
| `ProgramDatabase` | Значение взято из базы программы: климат, материалы, гликоль, продукты REHAU и т.п. |
| `Calculated` | Значение уже рассчитано существующим расчётным кодом приложения. |
| `Derived` | Значение получено из существующих данных без нового инженерного расчёта: форматирование, конвертация единиц, подпись, группировка. |

### 7.2 Отображение трассировки

В MVP трассировка должна быть видна в отчёте одним или несколькими способами:

| Способ | Где применять |
| --- | --- |
| Колонка `Источник` | Таблицы исходных данных, параметров и ключевых результатов. |
| Примечание к разделу | Когда группа значений имеет общий источник. |
| Приложение источников | Полный индекс значений для проверки. |

Для официального PDF рекомендуется показывать источник в ключевых таблицах и дополнительно включать компактное приложение "Источники значений".

### 7.3 Концепция модели значения

Ожидаемая модель может быть реализована как record/class в стиле проекта:

```csharp
public enum ReportValueSource
{
    UserInput,
    Project,
    ProgramDatabase,
    Calculated,
    Derived
}
```

```csharp
public sealed class ReportValue<T>
{
    public T Value { get; init; }
    public string Unit { get; init; }
    public ReportValueSource Source { get; init; }
    public string SourceDetail { get; init; }
}
```

Точная форма типов может отличаться, но каждое отображаемое значение должно иметь значение, единицу измерения, категорию источника и при возможности деталь источника.

## 8. Предупреждения

Предупреждения детального отчёта должны быть воспроизводимыми и основанными только на доступных данных программы.

Разрешённые основания:

| Основание | Допустимо |
| --- | --- |
| Существующие флаги валидации/предупреждений | Да |
| Существующие лимиты из базы программы | Да |
| Существующие ограничения из `ValidationConstants` или аналогичных источников | Да |
| Отсутствие обязательных данных для выбранного режима | Да |
| Новые инженерные пороги, придуманные для отчёта | Нет |
| Рекомендации агента без источника в программе | Нет |
| Нормативные ограничения без источника в проекте/базе | Нет |

Ожидаемая структура предупреждения:

```csharp
public sealed class CalculationReportWarning
{
    public string Code { get; init; }
    public string Severity { get; init; }
    public string Message { get; init; }
    public string SourcePath { get; init; }
    public IReadOnlyList<string> RelatedValues { get; init; }
}
```

MVP может использовать уровни `Info`, `Warning`, `Error`, если они соответствуют существующим проверкам или состоянию отсутствующих данных.

Если предупреждений нет, отчёт должен явно писать: `Предупреждения по доступным данным проекта и программы не сформированы.`

## 9. Структура детального отчёта

### 9.0 Обязательное раскрытие расчётных параметров

Детальный отчёт должен раскрывать не только итоговые числа, но и расчётные параметры, из которых эти числа получены. Это обязательное требование для официального инженерного отчёта.

Каждый расчётный параметр, выводимый в отчёте, должен иметь:

| Поле | Требование |
| --- | --- |
| Название | Пользовательское инженерное название параметра. |
| Обозначение | Формульное обозначение, если оно есть в коде или документации. |
| Физический смысл | Краткое описание, зачем параметр нужен в расчёте. |
| Единица измерения | Единица отображения в отчёте. |
| Источник значения | `UserInput`, `Project`, `ProgramDatabase`, `Calculated` или `Derived`. |
| Формула | Формула из существующего кода или документации. |
| Источник формулы | Файл документации, расчётный сервис или модель, где формула/значение подтверждены. |
| Где рассчитывается | Кодовый источник, если параметр считается программой. |
| Где используется | Последующие разделы отчёта, таблицы или расчётные блоки. |

Для повторяющихся сущностей, например контуров, формула и обозначения раскрываются один раз, а значения приводятся таблицей по всем контурам.

Если значение уже выводится программой, но формула ещё не найдена в коде или документации, реализация отчёта должна:

1. Вывести значение только как существующее `Calculated`-значение программы.
2. Указать источник значения.
3. Пометить формулу как `требуется привязка к существующей формуле`.
4. Не придумывать формулу и не добавлять новый расчёт.

Перед реализацией детального отчёта должна быть заполнена инвентаризация расчётных величин: `docs/calculation-parameter-inventory.md`. Реализация отчёта должна использовать этот файл как карту состава отчёта и формульных источников.

### 9.4 Методика и формулы

Раздел должен описывать только формулы и методику, которые уже есть в коде или документации проекта.

Источники формул при реализации:

| Источник | Назначение |
| --- | --- |
| `docs/Formulas_Snegotayanie.md` | Основные формулы снеготаяния. |
| `docs/Расхождения_с_Formulas_Snegotayanie.md` | Известные расхождения и уточнения. |
| `docs/Hydraulics_Analysis.md` | Гидравлическая методика и сверка. |
| Код расчётных сервисов | Фактически реализованные формулы. |
| `docs/инструкция/README v.2.1.md` | Терминология и пример полноты описания. |

Правила:

1. Формулы не должны придумываться в ходе реализации отчёта.
2. Если формула не найдена в существующем источнике, она помечается как `не включена в MVP`, а не восстанавливается по памяти.
3. Формула показывается один раз в разделе или в приложении.
4. Таблицы результатов ссылаются на формулы, но не повторяют подстановку для каждого контура.

### 9.5 Теплотехнический расчёт

Раздел должен включать:

| Блок | Содержание |
| --- | --- |
| Используемые формулы | Только формулы из существующего кода/документации. |
| Входные параметры | Температуры, R1, R2, LambdaE, труба, шаг, климатические параметры. |

Каждая таблица должна содержать значение, единицу и источник.

| Режим течения | - | `Calculated` |
| Удельные потери давления | Па/м | `Calculated` |
| Потери в трубе | Па или кПа, единообразно по отчёту | `Calculated` |
| Потери в распределителе | Па или кПа | `Calculated` |
| Потери в вентиле | Па или кПа | `Calculated` |
| Суммарные потери | Па или кПа | `Calculated` |
| Дросселирование/увязка | Па или кПа | `Calculated` |
| Обороты клапана | об. | `Calculated` |

Единицы давления должны быть единообразны внутри таблицы. Если исходные данные в программе хранятся в Па, а отчёт показывает кПа/мбар, это считается `Derived` для отображаемого значения.

### 9.7 Оборудование и спецификация

Раздел включает только доступные в состоянии программы значения.

| Значение | Источник |
| --- | --- |
| Спецификации коллекторов | `Project`, `ProgramDatabase` или `Calculated` |
| Тип коллектора | `Project` или `ProgramDatabase` |
| Количество контуров | `Project` |
| Суммарная мощность | `Calculated` |
| Суммарный расход | `Calculated` |
| Потери давления | `Calculated` |
| Kv | `Calculated` или `ProgramDatabase` |
| Общая длина трубы | `Calculated` |
| Количество РЗС/коллекторов | `Project` или `Calculated` |
| Насосные параметры, если доступны | `Calculated` |
| Расширительный бак, если доступен | `Calculated` |

Нельзя добавлять артикулы, паспортные данные или оборудование, если они не доступны через существующее состояние программы или базу продуктов.

### 9.8 Предупреждения и ограничения

Раздел выводится всегда.

Если предупреждения есть, для каждого предупреждения показываются:

| Поле | Описание |
| --- | --- |
| Код | Стабильный код предупреждения. |
| Уровень | Info/Warning/Error или существующий уровень проекта. |
| Объект | Проект, коллектор, контур, слой, параметр. |
| Сообщение | Человеческое описание. |
| Основание | Флаг, лимит, отсутствующее значение или источник данных. |
| Связанные значения | Ключевые значения, из-за которых сформировано предупреждение. |

Если предупреждений нет, выводится явная строка об отсутствии предупреждений.

### 9.9 Приложение: источники значений

Приложение должно быть компактным индексом значений отчёта.

| Колонка | Описание |
| --- | --- |
| Путь в отчёте | Раздел/таблица/имя значения. |
| Название | Отображаемое имя параметра. |
| Значение | Отображаемое значение. |
| Единица | Единица измерения. |
| Источник | Категория источника. |
| Деталь источника | Модель, свойство, база или описание, если доступно. |

### 9.10 Приложение: формулы и обозначения

Приложение содержит формулы один раз по расчётным областям:

| Область | Требование |
| --- | --- |
| Климат/исходные параметры | Только если в существующей документации есть формализованная логика. |
| Конструкция | Формулы сопротивления слоёв и связанные обозначения из существующих источников. |
| Теплотехника | Формулы снеготаяния/теплопередачи из существующих источников. |
| Гидравлика | Формулы потерь, расхода, режима течения и балансировки из существующих источников. |
| Оборудование | Только доступные алгоритмы подбора из существующих источников. |

## 10. Архитектура

### 10.1 Основные компоненты

| Компонент | Ответственность |
| --- | --- |
| `CalculationReportMode` | Режим отчёта: рабочий или расчётный/холодный. |
| `CalculationReportData` | Полный снимок детального отчёта, независимый от PDF/Markdown. |
| `CalculationReportDataBuilder` | Собирает отчёт из существующего состояния проекта и программы. |
| `ReportValueSource` | Категории источников значений. |
| `ReportValue<T>` | Значение, единица, источник, деталь источника. |
| `CalculationReportWarning` | Предупреждение отчёта. |
| `CalculationReportMarkdownRenderer` | Рендерит Markdown из `CalculationReportData`. |
| `CalculationReportPdfRenderer` | Рендерит PDF из `CalculationReportData`. |
| `ICalculationReportExportService` | Координирует экспорт детального отчёта в файл. |
| UI-команда | Отдельная команда детального отчёта, не заменяющая краткий PDF. |

### 10.2 Требования к builder

Builder должен:

1. Принимать `CalculationReportMode`.
2. Использовать только существующее состояние проекта/программы.
3. Выбирать `OperatingResult` или `DesignResult` в зависимости от режима.
4. Не выполнять новые инженерные расчёты.
5. Добавлять source metadata к отображаемым значениям.
6. Генерировать предупреждения только из существующих данных, лимитов, флагов и отсутствующих значений.
7. Быть детерминированным: одинаковый проект и режим дают одинаковые данные отчёта, кроме времени генерации.
8. По возможности зависеть от сервисов состояния/моделей, а не от WPF-контролов.

### 10.3 Требования к Markdown renderer

Markdown renderer должен:

1. Использовать только `CalculationReportData`.
2. Не выбирать режим и не рассчитывать значения.
3. Рендерить стабильный порядок разделов, коллекторов и контуров.
4. Показывать единицы измерения.
5. Показывать источники значений или приложение источников.
6. Показывать предупреждения и состояние "предупреждений нет".
7. Не заявлять ГОСТ/СП-соответствие без явного источника.

### 10.4 Требования к PDF renderer

PDF renderer должен:

1. Использовать тот же `CalculationReportData`, что и Markdown renderer.
2. Иметь нейтральный инженерный стиль MVP.
3. Не заменять текущий краткий `PdfExportService`.
4. Не выполнять расчёты и не выбирать режим.
5. Показывать те же смысловые разделы, что и Markdown.

## 13. Критерии приёмки

| ID | Критерий |
| --- | --- |
| AC-1 | Существующий PDF-экспорт "Результат" сохранён и не заменён детальным отчётом. |
| AC-2 | У детального отчёта есть отдельная команда/entrypoint. |
| AC-3 | Рабочий детальный отчёт использует `OperatingResult`. |
| AC-4 | Расчётный/холодный детальный отчёт использует `DesignResult`. |
| AC-5 | В MVP нет новых инженерных расчётов ради отчёта. |
| AC-6 | Все отображаемые численные значения имеют категорию источника. |
| AC-7 | Предупреждения имеют основание в существующих данных, лимитах, флагах или missing-data состояниях. |
| AC-8 | Отчёт не заявляет ГОСТ/СП-соответствие без явного источника. |
| AC-9 | Формулы показаны один раз по разделу/приложению, а контуры представлены таблицами. |
| AC-10 | Markdown рендерится детерминированно. |
| AC-11 | PDF и Markdown строятся из одной модели `CalculationReportData`. |
| AC-12 | `.smc` остаётся форматом проекта и не смешивается с экспортными отчётами. |
| AC-13 | Каждый расчётный параметр из `docs/calculation-parameter-inventory.md`, включённый в отчёт, имеет название, единицу, источник значения, формулу или явную пометку `требуется привязка к существующей формуле`. |
| AC-14 | Параметры из инвентаризации со статусом `Условно` не выводятся как полноценные расчётные результаты, пока не подтверждена их доступность в текущем состоянии программы. |
| AC-15 | Реализация отчёта не считается завершённой, если формула или warning-порог взяты из старой документации, но противоречат текущему коду или `docs/Расхождения_с_Formulas_Snegotayanie.md`. |

## 14. Рекомендуемая последовательность реализации

1. Зафиксировать тестами существующий краткий PDF-экспорт.
2. Пройти `docs/calculation-parameter-inventory.md` и привязать все пометки `требуется привязка к существующей формуле` к текущему коду или оставить их как явные ограничения MVP.
3. Добавить core-модели детального отчёта: mode, source, value, warning, formula, report data.
4. Написать тесты выбора режима и отсутствующих данных.
5. Реализовать `CalculationReportDataBuilder` без новых расчётов.
6. Написать тесты трассировки источников и полноты раскрытия расчётных параметров.
7. Написать тесты warning-модели.
8. Реализовать Markdown renderer.
9. Проверить Markdown на реальном проекте и сверить состав значений с Excel/ручной проверкой.
10. Реализовать PDF renderer поверх той же модели.
11. Добавить отдельную UI-команду детального отчёта и выбор режима.
12. Прогнать регрессию: краткий PDF, детальный Markdown, детальный PDF, сохранение/открытие `.smc`.

## 15. Ручная проверка перед релизом

| Проверка | Ожидаемый результат |
| --- | --- |
| Краткий PDF | По-прежнему формируется как отчёт "Результат". |
| Детальный отчёт рабочего режима | Использует рабочие гидравлические данные. |
| Детальный отчёт расчётного/холодного режима | Использует расчётные/холодные гидравлические данные. |
| Название и режим | Документ явно показывает тип отчёта и выбранный режим. |
| Методика | Указана внутренняя методика REHAU без неподтверждённого ГОСТ/СП-заявления. |
| Значения | Все числа совпадают с данными программы и ручной Excel-сверкой. |
| Трассировка | Ключевые значения имеют источник. |
| Предупреждения | Все предупреждения объяснимы существующими данными проекта/программы. |
| Формулы | Формулы есть один раз, контуры приведены таблицами. |
| Внешний вид PDF | Нейтральный инженерный документ, не маркетинговый дашборд. |
| `.smc` | Сохранение и открытие проекта не изменились. |

## 16. Открытые вопросы

| Вопрос | Предпочтение по умолчанию |
| --- | --- |
| Где разместить новую команду? | Рядом с текущим экспортом PDF, но с отдельным названием: "Детальный расчётный отчёт". |
| Markdown пользовательский или внутренний? | На MVP лучше оставить возможность сохранять `.md`, потому что он полезен для проверки и согласования. |

| Нужен ли фирменный стиль REHAU позже? | MVP нейтральный; брендинг можно добавить отдельной задачей после утверждения содержания. |
