## 2026-09-05 (Фаза 1Б, UI smoke-набор)

1. UI smoke-сценарий расчёта закладывается физически реалистичным: фикстура
   `v1-sample.smc` хранит расчётный холодный климат (−28 °C, ветер 5), при
   котором тепловой расчёт неосуществим в принципе (потребная подача > 100 °C —
   владелец: «нереалистичный сценарий закладываешь»). Для проверки расчёта
   временная копия приводится к рабочему режиму (−2 °C, ветер 3, подача 35 —
   ΔT в допуске), фикстура не мутируется.
   → Правило: smoke-проверки расчёта — на входах из рабочего диапазона
   приложения; синтетические данные фикстур не «дотягиваются» до прохода.
   Проверка: `tests/SnowMeltingCalculator.Tests/UiSmoke/README.md` + зелёный
   `--filter "Category=UiSmoke"`.

2. WPF-автоматизация через FlaUI: верхний MenuItem шапки открывается
   `ExpandCollapse.Expand` (Invoke не поддерживается — PatternNotSupportedException),
   пункты подменю — Invoke; `ValuePattern.SetValue` на WPF TextBox корректно
   триггерит биндинг с русской локалью («35,0» парсится запятой).
   → Правило: UI-тесты используют существующие AutomationId (контракт
   селекторного теста); новый каркасный ID добавляется вместе со строкой
   контракт-теста в одной фазе (ShellModulePlate, Фаза 1Б).
   Проверка: `ThermalAutomationIdSelectorContractTests` + smoke-набор.

3. Ф3 (2026-09-05): DataGridColumn — DependencyObject вне визуального/логического
   дерева: DataContext не наследует, `RelativeSource AncestorType` на колонке
   молча не разрешается; видимость колонок двухрежимной таблицы биндится
   через Freezable-прокси (`BindingProxy.Data`) на VM-свойство `IsFullMode`.
   Попутно: при выносе DataGrid из TabControl.ContentTemplate binding
   `ItemsSource="{Binding Circuits}"` молча теряет источник (свойство живёт
   на CollectorData) — таблица «пустая без ошибок» в UI; перепривязывается
   на `SelectedCollector.Circuits`.
   → Правило: биндинг к колонке/заголовку DataGrid — только через
   BindingProxy или явный Source; после изменения хоста таблицы проверять
   источник ItemsSource по DataContext нового хоста.
   Проверка: интерактивный смоук Ф3 + зелёный dotnet test.

4. Ревью Ф3 (2026-09-05): владелец отметил невидимый текст в поле города
   (Климат) и спросил, относится ли дефект к фазе. Диагноз — нет: Ф3 не
   трогала Климат и общие словари; причина —
   `CityAutoCompleteBox.xaml`: локальный `Padding="12,8"` поверх
   `RehauTextBoxStyle` (= `TextBox.Default`, Height 34) → контентная зона
   18px, текст клипуется (класс ADR-006 п.1, остаток перепривязки Ф2).
   Решение владельца: фикс — в Ф5, где механика города переписывается.
   → Правило: дефект из ревью фазы вне её объёма не чинится в фазе — по
   решению владельца записывается отложенным пунктом в раздел целевой
   фазы плана (`docs/design/redesign-plan.md` §Ф5, дополнение
   2026-09-05), чтобы гарантированно доехал до реализации.
   Проверка: при приёмке Ф5 поле города на каноне `.f .in` (34 / 10,0),
   текст ввода виден; строка-дополнение в §Ф5.

5. Ревью Ф3 (2026-09-05): «ввожу 100 — видно только 00» в редакторе ячейки
   таблицы. Причина — не вёрстка, а гонка SelectAll: `TextBoxBehavior.
   SelectAllOnFocus` ставил выделение отложенно (DispatcherPriority.
   ContextIdle), ContextIdle срабатывает между нажатиями быстрого набора:
   «1» → отложенный SelectAll выделил «1» → «0» заменил её → итог «00»
   вместо «100» (старое значение «80» при этом осталось в начале строки).
   → Правило: выделение текста при получении фокуса — синхронно в
   обработчике GotFocus/GotKeyboardFocus; отложенный дубль допустим только
   как страховка «текст пришёл позже фокуса» и обязан пропускаться, если
   пользователь уже начал ввод (флаг по PreviewTextInput, снимается на
   LostFocus).
   Проверка: интерактивный ввод «100»/«12»/«35» в редакторы ячеек и поля
   формы (скриншоты fase3-smoke-out), полный dotnet test зелёный.

6. Прогон Ф5 (2026-09-06): «приложение повисло на вкладке тепловой расчёт»
   при правке подачи; строки и HeroKPI «пляшут» шириной. Причина — не
   биндинги, а компоновочная петля: чипы результатов 2:1 (AspectRatio:
   Height = ActualWidth/2) живут в ScrollViewer с Auto-скроллом. Высота
   чипов зависит от ширины вьюпорта, а появление/скрытие скроллбара меняет
   ширину: скроллбар → чипы ниже → контент помещается → скроллбар скрыт →
   чипы выше → … WPF не детектирует цикл, UI-поток крутится в Measure/
   Arrange (вис), ширины карточек при этом ходят на ~17 px (толщина
   скроллбара). Зона узкая (контент впритык к вьюпорту), поэтому
   воспроизводится геометрией/DPI владельца и не ловится смоук-прогоном
   на фиксированном окне.
   → Правило: Aspect.Ratio (и вообще высота, вычисляемая из ширины)
   допустим только там, где контент не влияет на высоту прокрутки
   (фиксированный вьюпорт, горизонтальные ленты). В прокручиваемых вьюхах
   чипы/карточки — с фиксированной высотой (AspectRatio.Ratio=0 —
   поддержанное отключение) либо высотой от контента.
   Проверка: ThermalView — Thv.ResultChip (Height=96, Ratio=0), строки
   Auto; CPU процесса 0% после правки подачи на высотах окна 906/900/720
   (скриншоты p5-fix-*), полный dotnet test зелёный.

## 2026-09-06 (пересборка истории: docs/workspace мимо git)

1. Пуш на GitHub обрывался: в незапушенных коммитах (origin/master..HEAD,
   22 шт.) оказался бинарь docs/workspace (~138.7 МБ) — презентации,
   брендбук, скриншоты прогонов. Решение владельца: рабочие материалы
   docs/workspace больше не в git; незапушенные коммиты пересобраны без
   папки (worktree + cherry-pick + rm), сообщения и порядок 1:1; файлы
   остались на диске.
   → Правило: вспомогательные рабочие материалы (презентации, брендбук,
   скриншоты прогонов) — не в git: docs/workspace/ игнорируется; в
   коммиты фаз попадают только скриншоты-исключения, если владелец
   отдельно их назовёт.
   Проверка: правило docs/workspace/ в .gitignore;
   `git log origin/master..master --name-only --pretty=format: |
   grep -c '^docs/workspace'` → 0.

7. Полировка Ф7 (2026-09-06, приёмка владельцем): предупреждения валидатора
   — не «мягкие ошибки». Сообщение «УГВ < 1 м → используется λБ» описывает
   автоматику, к которой пользователю нечего применять, но склейка
   Warnings с Errors в один ValidationMessage красила шаг степпера ⚠ и
   статус-бар как ошибку — «нормальный режим» выглядел проблемой.
   → Правило: каналы разделяются — Errors валидатора → ValidationMessage
   (шаг ⚠, статус Error), Warnings → InfoMessage (нейтральная Info-плашка,
   шаг остаётся ✓). Для новых модулей — сразу два канала, не склейка.
   Проверка: ConstructionViewModelTests.Validate_WetGroundwater_
   WarningsGoToInfoChannel + скрин construction-wet-no-warning.

## 2026-09-06 (Фаза 8: миграция PDF-рендера QuestPDF → PDFsharp/MigraDoc 6.2.4)

8. PDFsharp/MigraDoc 6.2: альбомная страница после `DefaultPageSetup.Clone()`.
   Связка `pageSetup.PageFormat = PageFormat.A4` + `Orientation = Landscape`
   в 6.2 даёт портретную страницу (MediaBox 595×842) — контент, свёрстанный
   на 782 pt, обрезается по правому краю; на скриншоте выглядит как «пропавшие
   колонки», а причина — в установке страницы.
   → Правило: размеры страницы после Clone() задавать явно —
   `PageWidth = Unit.FromPoint(842); PageHeight = Unit.FromPoint(595)`;
   после генерации PDF проверять MediaBox (или рендер в PNG), а не только
   факт наличия файла.
   Проверка: baseline-new.pdf MediaBox `0 0 842 595`, рендер 1123×793
   (docs/workspace/fase8/).

9. PDFsharp 6.x официальный vs форк PdfSharpCore — API картинок مختلف.
   `ImageSource.FromBinary(name, byte[])` — API форка (PdfSharpCore/
   MigraDocCore); в официальном 6.2.x класса `ImageSource` нет, byte[]
   вставляется fileless base64-протоколом: `AddImage("base64:" +
   Convert.ToBase64String(bytes))`. То же с резолвером шрифтов: в
   Core-сборке 6.2 «из коробки» шрифты не резолвятся —
   `GlobalFontSettings.UseWindowsFontsUnderWindows = true` (один раз за
   процесс, до первого рендера).
   → Правило: API-факты о PDFsharp проверять по официальным докам
   docs.pdfsharp.net или по метаданным скачанного nupkg (XML-доки в
   lib/net8.0), не по статьям о форках.
   Проверка: PdfExportServiceTests.ExportResultsToPdfAsync_
   WithConstructionImage_IncludesBase64Image; рендер отчёта с кириллицей.

10. Прежде чем утверждать «X не происходит» — проверь реактивные хуки на всём
    пути публикации (2026-09-06, полировка шапочной «Рассчитать»).
    Агент по коду подписок CircuitsViewModel заключил, что гидравлика не
    пересчитывается при тепловом пересчёте, и построил «каскад» явным
    дожимом; ревью диффа нашло хук HydraulicsStateCoordinator.
    OnContextChanged → CalculateAll на публикацию валидного результата
    (с baseline) — явный вызов дублировал его, а посылка была ложной.
    → Правило: состояниеpublisher'а ищи у координаторов/контекстов, а не
    только у VM: grep по подпискам на Changed/ContextChanged в Services/Project
    перед выводами о цепочках пересчёта.
    Проверка: ревью диффа (P2-2/P2-3), HeaderCalculateCascadeTests (каскад
    хуком, без явного вызова).

11. WPF Application в тестах — процесс-глобален и владеет Dispatcher'ом
    (2026-09-06, HeaderCalculateCascadeTests).
    Фикстура создала `new Application()` на своём потоке; тесты
    EditorDialogService, обращающиеся к Application.Current.MainWindow со
    своего потока, получили VerifyAccess («владельцем является другой поток»)
    в зависимости от порядка прогонов.
    → Правило: VM/сервисным тестам Application не нужен; если нужен — только
    в фикстуре, которая его использует, и осознанно (thread-affinity
    распространяется на все последующие фикстуры процесса).
    Проверка: EditorDialogService + HeaderCalculateCascade вместе — зелёные.

## 2026-09-07 (мини-фаза PDF-PZ: PDF-версия пояснительной записки)

12. PDFsharp 6.2 (официальная Core-сборка): глобальный шрифтовый резолвер
    (`GlobalFontSettings.FontResolver`) можно установить только до первой
    шрифтовой операции процесса — после рендера любого PDF установка бросает
    InvalidOperationException. «Именованный» шрифт, отсутствующий в системе
    (Inter не установлен), без резолвера роняет рендер («No appropriate font
    found»). Делегация `PlatformFontResolver.ResolveTypeface` разрешена только
    изнутри установленного резолвера; байты платформенных шрифтов он
    регистрирует сам — `GetFont` у композитного резолвера зовётся только для
    своих граней. WPF-ресурсы читаются без Application через
    `ResourceManager("<Assembly>.g", assembly)` (корень «.g» — менеджер сам
    добавляет «.resources»).
    → Правило: бренд-шрифт подавать резолвером из встроенных TTF
    (CalculationReportPdfFontBootstrapper.EnsureInitialized — на старте DI,
    до любого рендера; при занятом резолвере — деградация на Arial);
    контент-пины PDF проверять обходом объектной модели MigraDoc, а не
    извлечением текста из PDF.
    Проверка: CalculationReportPdfRendererTests.InterResolver_ResolvesEmbeddedBrandFont;
    краткий PDF (Arial) — регрессия зелёная.

13. Визуальную приёмку PDF делать рендером страниц в PNG и судейством по
    чек-листу, а не только пинами текста: MigraDoc не переносит длинные

    ZWSP после «_» и шириной колонки по фактическим ширинам глифов Inter),

    артефакты (ADR-/DEC-T/wire), служебные статусы.
    Проверка: три прохода judge по 19 страницам docs/workspace/pdf-pz/ —
    pass; пины Render_FullReport_TextDoesNotContainCodeBasePaths.
