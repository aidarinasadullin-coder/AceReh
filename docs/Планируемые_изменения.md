## 1. Валидация отрицательной T_обратки (тепловой расчёт)

### Проблема

При T_подачи = 50 °C и T_средняя = 14.6 °C:
```
T_обратки = 2 × 14.6 − 50 = −20.8 °C
```
Программа не проверяет, что T_обратки отрицательна. Физически это означает, что теплоноситель в обратном трубопроводе может замёрзнуть.

### Предлагаемое решение

Добавить проверку в `ThermalCalculator.Validate()` или `ThermalViewModel.ValidateInput()`:
- Если `T_обратки = 2 × MeanTemperature − SupplyTemperature < 0 °C` → ошибка
- Текст: «Температура обратки (X °C) ниже 0 °C. Увеличьте температуру подачи, снизьте тепловую мощность или измените режим работы.»

### Приоритет

Высокий. Без этой проверки пользователь может получить заведомо неработоспособную систему.

## 2. Валидация ΔT (тепловой расчёт)

### Проблема

В коде два разных значения ΔT:

| Откуда | Значение | Куда идёт |
|--------|----------|-----------|
| `BuildThermalParameters()` (`ThermalViewModel.cs:329`) | **15.0 K (hardcoded)** | `ThermalParameters` → гидравлический расчёт |
| `Result.DeltaT = SupplyTemperature − ReturnTemperature` (`ThermalCalculator.cs:509`) | **Фактический** (напр. 14.8 K) | Отображается пользователю |

Гидравлика использует **15.0 K** независимо от фактического ΔT. Результаты близки (220 vs 222 л/ч в примере), но концептуально неверно.

В `ValidationConstants` есть `MaxDeltaT = 30.0 K`, но:
- Он проверяется для параметра 15.0 (заведомо проходит)
- Фактический ΔT (T_подачи − T_обратки) может превысить 30 K без предупреждения

### Предлагаемое решение

- Убрать жёстко зашитый `DeltaT = 15.0` из `BuildThermalParameters()`
- Рассчитывать ΔT после определения T_обратки
- Проверять ΔT на превышение `MaxDeltaT` (должно быть ≤ 30 K)
- Проверять, что при ΔT > 30 K скорость потока не падает ниже `MinVelocity`

### Приоритет

Средний. Связан с п. 1.

## 3. Проверка T_замерзания гликоля относительно t_cold_days_098 (гидравлика)

### Проблема

Согласно `docs/Formulas_Snegotayanie.md` (п. 11.13):
> Программа выдаёт ошибку, если температура замерзания (по таблицам ASHRAE) выше t_cold_days_098 (температура наиболее холодных суток с обеспеченностью 0.98)

В текущей версии эта проверка **не реализована**.

### Предлагаемое решение

- В `HydraulicInputData.Validate()` или в `CircuitsViewModel` при расчёте добавить: при `T_замерзания_гликоля > t_cold_days_098` → ошибка
- `t_cold_days_098` берётся из `ClimateData.ColdFiveDayTemperature` или напрямую из города

### Приоритет

Средний. Без этой проверки пользователь может выбрать гликоль, который замёрзнет в пик холодов.

| Файл | Константа | Значение |

Неясно, какая константа где используется. Это приводит к неоднозначным проверкам.

- Удалить дублирование — оставить только `ValidationConstants.MinVelocity`
- Обновить все места, использующие `HydraulicsConstants.MinVelocity`

### Приоритет

Низкий (косметический), но может привести к багам при расширении функционала.

## 5. Проверка max T_подачи для бетона (конструкция)

### Проблема

В `materials_db.json` у бетонных материалов стоит `max_supply_temp = 50 °C`. В `Construction.ValidateConstruction()` (строка 313) есть проверка:
```csharp
if (layer.Material?.MaxSupplyTemp.HasValue == true)
{
    result.AddWarning($"Материал '{layer.Material.Name}': максимальная температура подачи {layer.Material.MaxSupplyTemp}°C");
}
```
Но это только **предупреждение**. T_подачи не блокируется.

### Предлагаемое решение

- Перенести проверку max T_подачи из `Construction.ValidateConstruction()` в `ThermalViewModel.ValidateInput()`, где она будет блокировать расчёт при превышении.
- Проверять не только наличие материала с ограничением, но и фактическую T_подачи.

### Приоритет

Низкий (предупреждение уже есть), но желательно для полноты.

## 8. Команда «Создать новый расчет» в меню «Файл» (UI)

### Проблема

Отсутствует возможность начать расчёт с нуля без перезапуска программы. Пользователь, завершивший один проект, вынужден закрывать и открывать приложение заново.

### Предлагаемое решение

Добавить в меню/кнопку **«Файл»** команду **«Создать новый расчет»** со следующим поведением:

1. При вызове команды проверяется, были ли внесены изменения в текущий расчёт (флаг `IsDirty` или аналогичный).
2. Если изменения **есть** — показывается диалоговое окно подтверждения:
   > *«Файл не сохранён. Сохранить сейчас?»*  
   > **Варианты:** Да / Нет / Отмена
   - **Да** → сохранить текущий расчёт, затем закрыть
   - **Нет** → закрыть без сохранения
   - **Отмена** → отменить операцию, оставить текущий расчёт открытым
3. Если изменений **нет** (чистый проект) — диалог не показывается, сразу создаётся новый расчёт.
4. Текущий расчёт закрывается, все поля сбрасываются к значениям по умолчанию (аналогично начальному состоянию при запуске).
5. История изменений (`Undo`/`Redo`) очищается.

### Затрагиваемые файлы

- `Views/MainWindow.xaml` — добавить пункт меню
- `ViewModels/MainViewModel.cs` — команда `NewCalculationCommand`
- `Services/NavigationService.cs` — логика открытия/закрытия расчёта с сохранением
- Возможно: общий диалог `SaveChangesDialog.xaml` (переиспользовать для других сценариев — выход, открыть)

### Приоритет

Высокий. Базовая пользовательская функциональность, без которой программа не соответствует минимальным ожиданиям от настольного приложения.

## 9. Переупорядочивание слоёв над/под трубой (UI, расчёт, визуализация)

### Проблема

В таблицах слоёв (над трубой / под трубой) невозможно изменить порядок слоёв. Порядок слоёв критически важен — он влияет на:

- **Расчёт** термического сопротивления (R-значения): последовательность суммирования должна соответствовать физическому расположению
- **Визуализацию** в представлении конструкции: слои отображаются сверху вниз в порядке таблицы
- **Результаты** на вкладке результатов: тепловые характеристики привязаны к позиции слоя

### Предлагаемое решение

Добавить кнопки **«Вверх»** / **«Вниз»** (или стрелки ▲ ▼) для каждой строки в таблицах слоёв над трубой и под трубой:

1. **UI (ConstructionView.razor / xaml):**
   - В каждой строке таблицы добавить две кнопки: ▲ (переместить вверх) и ▼ (переместить вниз)
   - Первый элемент не может быть перемещён вверх (кнопка ▲ неактивна)
   - Последний элемент не может быть перемещён вниз (кнопка ▼ неактивна)
   - Альтернатива: drag-and-drop (более сложная реализация)

2. **ViewModel / Model:**
   - Методы `MoveLayerUp(int index)` / `MoveLayerDown(int index)` в `ConstructionViewModel`
   - При перемещении: `ObservableCollection<Layer>` обновляется, флаг `IsDirty = true`
   - Пересчёт `TotalResistanceAbove / TotalResistanceBelow` и обновление зависимых полей

3. **Расчёт (`ThermalCalculator`):**
   - Предполагается, что `Layer.AbovePipe` / `Layer.BelowPipe` уже корректно группируются
   - Проверить, что порядок в `BuildAbovePipeLayers()` / `BuildBelowPipeLayers()` соответствует порядку в UI после перестановки

4. **Визуализация (конструкция):**
   - Графическое отображение слоёв должно обновляться после перестановки
   - Подписи слоёв, цвета, толщина — синхронизированы с новым порядком

5. **Вкладка «Результаты»:**
   - Таблица результатов по слоям должна отражать актуальный порядок
   - Обновить привязку данных при изменении порядка

### Затрагиваемые файлы

- `Views/ConstructionView.razor` или соответствующий xaml — кнопки перемещения
- `ViewModels/ConstructionViewModel.cs` — команды `MoveLayerUpCommand`, `MoveLayerDownCommand`
- `Services/CalculationService.cs` — возможно, требуется перестроить цепочку слоёв
- `Views/VisualizationView.razor` — обновление визуализации при перестановке
- `Views/ResultsView.razor` — обновление таблицы результатов

### Приоритет

Средний. Улучшение UX — без этой функции добавление слоя в неправильном порядке требует удалить и добавить заново, что неудобно.
