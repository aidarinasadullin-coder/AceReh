# Спецификация детального расчётного отчёта v2 («Пояснительная записка»)

> **Статус:** принята владельцем (согласование скелета 2026-09-06, решения
> зафиксированы в журнале ниже). База: `docs/report-spec.md` (v1, реализованный
> MVP), README v.2.3 kimi (эталон содержания),
> `docs/calculation-parameter-inventory.md` (реестр величин).
>
> **План реализации:** `docs/plans/2026-09-06-report-v2-plan.md`.

## 1. Назначение и проблема

Детальный отчёт v1 (реализован: сплит-кнопка «Отчёт PDF ▾» → Markdown рабочий/
холодный режим, `src/Services/Reports/Calculation/`) выводит таблицы-сводки.
Недостатки против цели «пояснительная записка»:

1. Формулы — один раз в приложении; хода расчёта «формула → подстановка →
   результат» нет.
2. Большинство тепловых величин рендерятся нулями: wire-контракт DEC-T08
   сохраняет в `.smc` только 8 полей результата; α, Qтаяния, Qконв, RFb, RD,
   m, ηR, JHmü, расходы не сохраняются, `ThermalSectionBuilder` заполняет их
   константами 0.0.
3. Константы расчёта дублируются в билдере числами — источник истины должен
   быть один (код `ThermalCalculator`).

Цель v2: отчёт уровня пояснительной записки — исходные данные и выбранное,
методика с формулами, подстановка реальных значений проекта, промежуточные
величины, проверки, примечания. Эталон содержания — README v.2.3 kimi
(блоки «Что рассчиталось автоматически»).

## 3. Источник данных отчёта

### 3.1 Канонический снимок сессии

Все тепловые величины берутся из `ProjectSession.ThermalState.Snapshot`
(`ThermalResultSnapshot` — DEC-T01: полный набор α, MeltingHeat, RadiationHeat,
ConvectionHeat, ExcessTemperature, RFb, RD, ParameterM, EfficiencyEtaR,
MassFlowRate, VolumeFlowRate, ValidationErrors). Это сценарий «посчитал →
выгрузил»: полный отчёт без пересчёта.

Гидравлика — из `HydraulicsState`/`ProjectData` по выбранному режиму
(`OperatingResult`/`DesignResult`), как в v1.

### 3.2 Контрольный пересчёт (fallback)

Если расширенные величины снимка нулевые (открыт файл, сохранённый до загрузки
программы, и экспорт вызван до пересчёта), отчётный провайдер один раз вызывает
существующий `ThermalCalculator.Calculate(inputs, climate, construction)` по
входам из проекта. Правила:

- пересчёт — только для отчёта; результат в каноническое состояние **не
  пишется**, события не публикуются, dirty не создаётся;
- `ThermalCalculator.Calculate` — детерминированная функция без зависимостей
  от UI; вызов вне расчётного пайплайна безопасен;
- пересчитанные PowerUp/PowerTotal/ΔT сверяются с сохранёнными 8 полями
  (снимок/`ProjectData`); расхождение сверх точности округления → примечание
  в отчёте «значения получены контрольным пересчётом, проект сохранён
  предыдущей версией методики»;
- **правило сборки входов пересчёта**: `ThermalInputs` собирается ровно как
  `ThermalViewModel.BuildThermalInputs` — Mode/SupplyTemperature/
  GroundTemperature/Pipe (через `ToPipeType()`)/PipeSpacing из
  `ThermalState.Snapshot.Inputs`; LambdaE — из
  `ConstructionState.CurrentProjection`; плотность/теплоёмкость теплоносителя —
  **дефолты `ThermalInputs`** (1053 кг/м³ / 3.39 кДж/(кг·К)), как в основном
  пайплайне (эти поля нигде не настраиваются и не сохраняются). Иначе
  пересчёт разойдётся с фактическим пайплайном и сверка даст ложные
  примечания; рядом с расходами пересчёта — пометка о дефолтном теплоносителе;
- **валидность пересчёта**: если пересчёт вернул `IsValid=false`
  (невалидная комбинация входов в файле, выход климата за диапазон) —
  тепловые шаги рендерятся маркером «нет данных» + MISSING_THERMAL_DETAIL,
  `ValidationErrors` пересчёта выводятся в раздел «Проверки» (как В7);
- признак источника тепловых величин (снимок / контрольный пересчёт)
  отображается в отчёте;
- `reportDate` передаётся в экспорт-сервис параметром (сейчас не передаётся —
  в заголовке печатается 0001-01-01).

### 3.3 Сценарии

| Сценарий | Поведение |
| --- | --- |
| Посчитал → выгрузил | Полный отчёт из снимка, без пересчёта |
| Открыл файл **с валидным сохранённым результатом** → сразу выгрузил | Полный отчёт через контрольный пересчёт + примечание (8 wire-полей есть, runtime-поля нулевые) |
| Открыл файл **без результата** → сразу выгрузил | Финализация загрузки уже пересчитала канонику — отчёт из снимка, без примечания о пересчёте |
| Изменил входы → не пересчитал → выгрузил | Предупреждение REPORT_INPUTS_STALE |
| Контрольный пересчёт не дал валидного результата (`IsValid=false`) | «нет данных» + MISSING_THERMAL_DETAIL + `ValidationErrors` пересчёта в разделе «Проверки» |

**Предикат REPORT_INPUTS_STALE** (ревью P2-1/P2-2): тепловой
`ThermalState.Snapshot.Status.Phase == NeedsRecalculation` **и** результат
не нулевой (`Result != null`) — то есть «результат сохранён, но устарел».
Общий `ProjectSession.IsDirty` не используется (он срабатывает на любые
правки, включая номер проекта, и снимается сохранением файла). Успешный
контрольный пересчёт по текущим входам исключает stale: upstream-инвалидация
(результат обнулён + NeedsRecalculation) даёт полный отчёт из пересчёта без
противоречивого предупреждения.

### 3.4 Свойства теплоносителя (гликоль)

Свойства теплоносителя (плотность ρ, теплоёмкость c_p, вязкость ν;
теплопроводность λ и число Прандтля Pr) фиксируются в каноническом снимке
`HydraulicsState` при расчёте гидравлики — для Operating и Design (В13,
вариант А; ADR-013: runtime-каноника, wire-контракт `.smc` не расширяется,
DEC-T08 не затронут). Заполнение снимка — в пайплайне гидравлики в точке
обновления снимка результатами (те же входы, что переданы в
`CircuitsCalculator`: тип/концентрация из `HydraulicInputData`,
`operatingTemperature`/`designTemperature`); пин: снимок ==
`GetProperties(входы)` — сервис singleton, повторный вызов детерминирован.
Билдер ПЗ читает свойства из `ProjectSession` (Derived-читатель, ADR-013)
и сам `GlycolDataService` не вызывает.

Fallback (по образцу §3.2): если снимок не содержит свойств (файл старой
версии), отчётный провайдер выполняет **ровно один** контрольный вызов
`GetProperties(тип, концентрация, T_режима)` по входам каноники; рядом с
величинами — примечание «свойства теплоносителя получены контрольной
интерполяцией»; результат вызова в каноническое состояние не пишется,
события не публикуются, dirty не создаётся. Концентрация 0 % → свойства
воды (реализовано в сервисе). Выход параметров за диапазон базы → маркер
«нет данных» (В2) + предупреждение.

## 4. Модель: шаги расчёта

Новая сущность в `ReportSections.cs`:

```csharp
public sealed class CalculationStep
{
    public string Key { get; init; }            // стабильный ключ ("thermal.alpha")
    public string Title { get; init; }          // «Коэффициент теплоотдачи α»
    public string FormulaText { get; init; }    // "α = 2.26·(tП − tH)^0.33 + 2.6·vH"
    public string SubstitutionText { get; init; } // "α = 2,26·(5 − (−15))^0,33 + 2,6·3,1"
    public ReportValue<double> Result { get; init; } // значение + единица + источник
    public string? Note { get; init; }          // примечание (смысл, источник)
    public IReadOnlyList<ReportValue<double>> Inputs { get; init; }
}
```

Правила:

1. `SubstitutionText` собирается билдером из тех же `ReportValue`, что идут в
   таблицы раздела (категория Derived — форматирование, не расчёт). Числа в
   шаге и в таблицах не могут разойтись по построению. Метаданными источника
   чисел подстановки считаются `Inputs` шага + публичные константы п. 5;
   тест-пин: множество чисел `SubstitutionText` равно множеству значений
   `Inputs` (плюс константы формул).
2. Рендер (Markdown и будущий PDF) не вычисляет и не выбирает значения.
3. Шаги с отсутствующими данными рендерятся маркером «нет данных» (В2).
4. Секции модели: `ThermalSection.Steps`, `ConstructionSection` — шаги R1/R2,
   `HydraulicsSection.ReferenceCircuit` — цепочка шагов референсного контура
   и пример балансировки, таблица констант расчёта.

## 5. Раскрытие констант

Приватные константы `ThermalCalculator` (SnowDensity 900, IceHeatCapacity 2100,
IceMeltingHeat 330000, WaterHeatCapacity 4200, RodCoefficient 0.6,
StefanBoltzmann 5.77e-8, EmissionCoefficient 0.055, AlphaBottom) и
гидравлические константы/лимиты делаются доступными отчётному билдеру
**без изменения значений**. Дублирование чисел в билдере отчёта удаляется.

Решение по существующему дубликату (ревью P2): в `src/Core/Constants/
ThermalConstants.cs` все 8 перечисленных констант уже объявлены публично с
**идентичными значениями**, но `ThermalCalculator` их не использует. R1
переключает `ThermalCalculator` на `ThermalConstants` (значения равны —
T2-01 подтверждает неизменность расчёта), дубль-литералы в калькуляторе
удаляются; **константы `ThermalConstants.SurfaceTempMelting/Prevention/
AntiIce` (2/0/−2) запрещены как источник температуры поверхности** — они
противоречат фактической логике `(int)inputs.Mode` = 3/5/7.

Карта гидравлических констант (ревью P2): лимиты оборотов —
`ValveTurnsCalculator.GetMaxTurns`; Kv клапанов — `ValveTurnsCalculator.KV_*`;
границы Re/шероховатость — `FlowRegimeCalculator` (публичные); лимиты
v/R/Δp/ΔT — `ValidationConstants` + `CircuitTemperatureResult.MaxPressureLossPerMeter`;
коэффициенты формул Dp — литералы `CircuitsCalculator` (раскрыть в константы
или ссылаться только при совпадении значений). **`HydraulicsConstants` как
источник для отчёта не использовать без построчной сверки** — его значения
расходятся с кодом (MaxTurns_HKV_D = 4 против фактических 2.5;
MinVelocity = 0.5 против фактических 0.1).

Внимание: значения README v.2.3 kimi (893/2050/334000/4180) — из прежней
версии кода; отчёт и эталонная сверка используют текущие значения кода
(источник истины — код, AC-15 спецификации v1).

## 6. Структура документа

Нумерация разделов стабильная.

1. **Титульный блок** — объект, номер, режим, дата, методическая оговорка
   (внутренняя методика REHAU; без ГОСТ/СП-заявлений).
2. **Краткая сводка** — как v1.
3. **Исходные данные и принятые решения** — климат (с пометками
   «введено пользователем / база программы / данные СП»), режим поверхности,
   пирог таблицей, труба, шаг, гликоль.
4. **Конструкция** — слои + шаги: правило λА/λБ по УГВ, R1 и R2 с подстановкой
   по слоям, λE.
5. **Теплотехнический расчёт — пошагово**: α → Qтаяния (константы таблицей) →
   Qконв → PowerUp → RFb → m → ηR (коэффициенты A–E таблицей) → JHmü →
   Tсредняя → Tобратки/ΔT → qD → qTotal → расходы (массовый/объёмный на м²).
6. **Гидравлический расчёт** — свойства теплоносителя (ρ, cp, ν по режиму);
   цепочка шагов на референсном контуре (В4): Q_HK → V̇ → v → Re → λ → R →
   DpRohr → DpVerteiler → DpVent → DpGesamt; пример балансировки: Δp дросселя
   → обороты (правило вычитания по типу коллектора HKV-D/IV; Kv-формула —
   без подстановки: Kv контура не сохраняется в проекте — пометить);
   примечание о семантике DpVent; подбор типов коллекторов (алгоритм + факты);
   сводные таблицы по коллекторам/контурам — как v1.
7. **Оборудование** — KPI, спецификации (как v1).
8. **Проверки и предупреждения** — существующие лимиты (v, R, Δp, ΔT, обороты)
   со статусом по каждому коллектору; предупреждения v1; примечания валидации
   из `ValidationErrors` снимка (В7); REPORT_INPUTS_STALE, MISSING_THERMAL_DETAIL.
9. **Примечания** — справочные значения из баз только при наличии источника
   (tзамерзания гликоля и т.п.).
10. **Приложения** — формулы, обозначения, источники значений (как v1).
    Приложение «Обозначения» — по словарю обозначений ПЗ
    `docs/design/glossary-report-designations.md` (В16): полный охват
    выводимых величин, 5 колонок — обозначение → русское определение →
    единица → источник (эталон kimi / Формулы / Ф3 / код / «новое») →
    немецкое происхождение (только для гидравлики); пирамида источников и
    четыре правила конфликтов — в преамбуле словаря. Кодовые имена домена
    в ПЗ не выводятся (В16/В17: `DpRohr`→`Δp_трубы`, `DpVerteiler`→
    `Δp_колл`, `DpVent`→`Δp_клап`, `DpGesamt`→`Δp_всего`,
    `zu_dr`→`Δp_дросс`, `PowerDown`→`q_D`); обозначения эталона
    (`JHmü`, `RFb`, `PowerUp`, `ṁ`) легитимны и расшифровываются в
    приложении.

Режимы: `Operating` — полный документ; `DesignCold` — краткая тепловая справка
(В3: Tсредняя, ΔT — контекст вязкости и ламинарного режима) + полный
гидравлический расчёт `DesignResult` + сравнительная таблица «рабочий vs
холодный пуск» (ν, Re, λ, Δp по коллекторам, кратность роста).

## 7. Рендер, форматирование, брендбук

### 7.1 Приоритет: строгость расчётного документа

Наследуется правило v1 (§2, «Стиль MVP»): **нейтральный инженерный документ** —
заголовки, таблицы, единицы, предупреждения, приложения. Без маркетингового и
дашбордного оформления. Брендбук применяется в пределах, не разрушающих
инженерную строгость: бренд-элементы допустимы в титуле/колонтитулах и
служебных элементах; расчётное содержание (таблицы, формулы, подстановки,
статусы проверок) остаётся строгим и монохромно-читаемым — цвет не является
единственным носителем смысла (документ печатается, в т.ч. ч/б).

### 7.2 Применение брендбука по форматам

Источник: `docs/design_guidelines.md` (РУКОВОДСТВО ПО ДИЗАЙНУ РЕХАУ ДЛЯ WPF).

| Формат | Бренд-применение |
| --- | --- |
| Markdown (эта фаза) | Текстовый формат: логотип/цвет неприменимы. Бренд ограничен: наименование «РЕХАУ» кириллицей в титуле/методической оговорке (решение владельца №2 редизайна); нейтральная типографика Markdown |
| PDF (будущая мини-фаза) | Шрифт Inter (начертания по гайдлайну; резерв — по гайдлайну, для печатной продукции Inter обязателен); логотип `РЕХАУ_logo.svg` в колонтитуле (правила §7.1 гайдлайна: светлый фон, отступ 20% высоты, не растягивать); акцентный цвет — Активный Красный `#E50040` только в бренд-элементах (линия шапки), не в расчётных таблицах; семантические цвета (Умный Зелёный `#4FC7B5`, Ошибка `#D32F2F`, Предупреждение `#FF9800`) — только как дополнение к текстовым статусам ✅/❌/⚠; таблицы — серые границы, без заливки строк; баланс цветов 80/10/10; **без ссылок на кодовую базу** (решение владельца, 2026-09-07): пути к классам/свойствам кода (SourceDetail, источник констант-таблицы, SourcePath приложения формул) в PDF не выводятся — трассировка в PDF остаётся в инженерных категориях («введено пользователем», «база программы», «рассчитано программой», «данные СП»); полная кодовая трассировка сохраняется в Markdown как техническом формате |

### 7.3 Форматирование и детерминизм

- Markdown — целевой формат фазы; детерминированность: одинаковый проект+режим
  → одинаковый вывод (кроме даты, передаваемой параметром).
- Числа: запятая — десятичный разделитель, пробел — разделитель тысяч (В6).
  Каноническая культура приложения **`AppCulture.Culture`** (`src/Core/
  AppCulture.cs`, pinned ru-RU; решение владельца 2026-09-04, пин
  `RussianNumberCultureTests`, Ф8 использует её же в PDF-рендере) —
  самостоятельный NumberFormatInfo не вводится; культура применяется и в
  таблицах, и в текстах предупреждений.
- Единицы давления единообразны внутри таблицы (Па), мбар — в сводках.
- Точность табличных чисел (В9, вариант Б): каждая табличная
  `ReportValue<double>` несёт `int? Decimals`, назначаемый билдером по
  единице величины; рендер (Markdown и PDF) — `value.Decimals ??
  TableFormat`; дефолт `TableFormat` — «N2» (жёсткий «N3» снят). Культура
  (`AppCulture.Culture`, ru-RU pinned) и `ReportNumber` не меняются.
  Нулевое значение → маркер «нет данных» только когда `!ZeroIsValid`
  (В14: `Throttling = 0` референсного контура — валидное значение, «0»).
  Семантика В2 (уточнение по независимому ревью P1–P2, 2026-09-07):
  «нет данных» — для заглушек нехранённых величин и результатов без
  хранения; доменно-валидные нули входов — хранимые значения и рендерятся
  «0» (`ZeroIsValid = true`): t_H = 0 °C (−50…+10), ветер 0 м/с
  (`ValidationConstants.MinWindSpeed = 0`), влажность 0 % (не валидируется,
  не участвует в расчёте), интенсивность снегопада 0 мм/ч (0…20),
  t_G = 0 °C (−10…30), уровень грунтовых вод 0 м (0…10), концентрация
  гликоля 0 % — вода (спека §3.4). Заглушка `ColdPeriodDays` («условно:
  данные отсутствуют») остаётся «нет данных».
- Таблица «единица → знаки» (В9, фиксируется для билдеров):

  | Единица | `Decimals` |
  | --- | --- |
  | шт, контур | 0 |
  | мм, Вт, Па | 0 |
  | м, °C, м² | 1 |
  | кВт, м³/ч, л | 2 |
  | λ, R, ν, σ | по текущим правилам (не ухудшать) |
  | Re | 0 |
  | скорость | 2 |

  Исключения сохраняются: расчётные константы — свои `Decimals` (таблица
  констант); λ в сравнении режимов — явный N3 (не терять значащую цифру);
  подстановки — позначальные (каждое число несёт свои знаки).
- Маркер «нет данных» — единая константа рендера.
- Терминология заголовков/подписей v2 — по глоссарию фазы 3 редизайна
  (приёмка фазы 8 требует терминологию отчётов по глоссарию Ф3).
- Упоминание QuestPDF в doc-комментарии рендера не восстанавливается
  (фаза 8 снимает его).
